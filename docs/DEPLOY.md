# Развёртывание на VPS

Один сервер — одно учреждение. Колонок арендатора в таблицах нет, и это
решение волны 8: цена перенесена из схемы в эксплуатацию и платится явно.

## Что нужно от сервера

| | Минимум | Рекомендуемо | Почему |
|---|---|---|---|
| Ядра | 2 | **4** | Расшифровка часового приёма занимает минуты и должна идти, не задевая консоль |
| Память | 2 ГБ | **8 ГБ** | Postgres, приложение и модель `small` в памяти одновременно |
| Диск | 20 ГБ | **80 ГБ** | Записи приёмов: час разговора ≈ 30 МБ в сжатом виде |
| ОС | Debian 12 / Ubuntu 22.04+ | | нужен только Docker |

**Про расшифровку отдельно.** whisper.cpp на процессоре работает примерно со
скоростью разговора: часовой приём — около часа счёта на двух ядрах моделью
`small`. Восемь приёмов за день расшифровываются к утру следующего, и это
нормальный режим: стенограмма нужна к разбору, а не к концу приёма. Если
нужна быстрее — берите больше ядер, а не меньшую модель: `tiny` и `base` на
украинском и русском дают текст, который приходится переписывать целиком.

## Первая установка

Репозиторий приватный, поэтому серверу нужен ключ на чтение. Заводится он
на самом сервере — закрытая часть никуда не уезжает:

```sh
ssh-keygen -t ed25519 -f ~/.ssh/quizzy_deploy -N "" -C "quizzy@$(hostname)"
cat ~/.ssh/quizzy_deploy.pub
```

Открытую часть добавьте в репозиторий: Settings → Deploy keys → Add,
**без** права записи. И научите ssh ею пользоваться:

```sh
cat >> ~/.ssh/config <<'EOF'
Host github.com
  IdentityFile ~/.ssh/quizzy_deploy
  IdentitiesOnly yes
EOF
```

Дальше всё делает один скрипт:

```sh
git clone git@github.com:4booser/Quizzy.git /opt/quizzy
cd /opt/quizzy
sudo ./scripts/vps-setup.sh polypsy.ink
```

Он ставит Docker, заводит `.env.docker` со случайными паролями, поднимает
стек, **проверяет что политики строк действуют и шифрование включено** и
заводит первого администратора, печатая его пароль один раз.

Пароли генерируются алфавитом base64url. Это не придирка: они попадают в
строку подключения вида `postgres://user:ПАРОЛЬ@host/db`, а обычный base64
даёт «/» и «+» — первый обрывает адрес на месте пароля.

Скрипт идемпотентен и **не перегенерирует пароли** на повторном запуске.
Перегенерация `ENCRYPTION_KEY` на работающем экземпляре означала бы, что
все зашифрованные поля больше не читаются — ни ФИО, ни заключения.

### Если ставить руками

```sh
curl -fsSL https://get.docker.com | sh
cp .env.docker.example .env.docker   # и заполнить
```

Заполнить `.env.docker`. Три значения обязаны быть случайными и разными:

```sh
head -c 24 /dev/urandom | base64   # POSTGRES_PASSWORD
head -c 24 /dev/urandom | base64   # APP_DB_PASSWORD
head -c 32 /dev/urandom | base64   # JWT_SECRET
```

И отдельно — ключ шифрования полей. **Задайте его сразу.** Без него ФИО,
даты рождения, свободные ответы и заключения пишутся в базу открытым
текстом; включить шифрование потом можно (`bun run db:encrypt`), но всё,
что успело записаться открытым, до этого момента лежало открытым.

```sh
echo "v1:$(head -c 32 /dev/urandom | base64)"   # ENCRYPTION_KEY
```

Ключ шифрования **не хранится в снимках базы** и не восстанавливается. Его
потеря означает потерю всех зашифрованных полей — положите копию туда же,
где храните доступы к серверу.

Дальше:

```sh
# 4. Запуск. Первый занимает время: собираются образы и качается модель
docker compose --env-file .env.docker up -d --build

# 5. Первый администратор
docker compose --env-file .env.docker exec api bun apps/api/src/install.ts
```

## Домен и TLS

До покупки домена всё работает по IP на `:80`. После — впишите домен в
`SITE_ADDRESS` и перезапустите консоль:

```sh
# A-запись домена должна указывать на IP сервера ДО этого шага:
# сертификат выдаётся по факту владения, и без записи выдача не пройдёт
docker compose --env-file .env.docker up -d web
```

Caddy сам получит сертификат Let's Encrypt и будет его продлевать. Порты 80
и 443 должны быть открыты — 80 нужен и после перехода на https, для
продления.

Заодно впишите тот же адрес в `CORS_ORIGINS` и `CONSOLE_URL`.

## Выкатка обновлений

Настраивается один раз, дальше — тег в git.

**Секреты репозитория** (Settings → Secrets → Actions):

| Секрет | Что это |
|---|---|
| `VPS_HOST` | адрес сервера |
| `VPS_USER` | пользователь с правом запускать docker |
| `VPS_PATH` | каталог установки, например `/opt/quizzy` |
| `VPS_SSH_KEY` | закрытый ключ для входа (заведите отдельный, только для выкатки) |
| `VPS_KNOWN_HOSTS` | вывод `ssh-keyscan <host>`, снятый один раз с доверенной машины |
| `SITE_ADDRESS` | домен консоли — по нему проверяется, что выкатка удалась |

`VPS_KNOWN_HOSTS` берётся из секрета, а не снимается с сервера в момент
выкатки: `ssh-keyscan` на живом соединении принимает любой ключ, включая
подменённый, и проверка превращается в её видимость.

На сервере в `.env.docker` добавьте:

```
QUIZZY_IMAGE_PREFIX=ghcr.io/4booser/quizzy
QUIZZY_VERSION=latest
```

и разрешите серверу читать реестр:

```sh
echo "<токен с правом read:packages>" | docker login ghcr.io -u 4booser --password-stdin
```

Дальше выкатка — это:

```sh
git tag v1.2.0 && git push origin v1.2.0
```

Порядок в выкатке: тесты → сборка образов → **снимок базы** → миграции и
перезапуск → проверка, что приложение отвечает. Снимок именно перед
миграциями: переключением тега схема назад не откатывается, и старый образ
на новую схему не встанет.

## Резервные копии

`scripts/backup.sh` кладёт снимок и проверяет, что он читается. Раз в сутки:

```sh
sudo tee /etc/cron.d/quizzy-backup <<'EOF'
0 3 * * * root cd /opt/quizzy && ./scripts/backup.sh >> /var/log/quizzy-backup.log 2>&1
EOF
```

**Снимок без проверки восстановлением — это не резервная копия, а надежда.**
Раз в месяц прогоняйте `scripts/verify-backup.sh`: он поднимает копию в
отдельной базе и проверяет, что схема и данные на месте.

Отдельно от базы копируйте:

- `ENCRYPTION_KEY` — без него зашифрованные поля не прочитать ничем;
- том `recordings` — записи приёмов лежат файлами, в снимке базы их нет.

## Что проверить после первого запуска

```sh
# 1. Политики строк действуют. В журнале должно быть «rls active».
docker compose --env-file .env.docker logs api | grep rls

# 2. Шифрование включено. Строки «crypto.disabled» быть не должно.
docker compose --env-file .env.docker logs api | grep crypto

# 3. Расшифровщик нашёл модель.
docker compose --env-file .env.docker logs transcriber | tail -3
```

Первый пункт — самый важный и самый незаметный. Приложение обязано
подключаться к базе ролью `quizzy_app`, которая таблицами не владеет:
владелец в PostgreSQL обходит политики строк, и с ним все сорок семь политик
остаются на месте, но каждый видит всё. Отличить это от исправной работы
нельзя ничем — запросы отрабатывают, экраны рисуются. Поэтому сервер в
production такой запуск не принимает и говорит, что делать.

## Вход через Google

Дополнительный способ входа, а не замена паролю. Пока в окружении пусто —
способа просто нет, и кнопка не рисуется.

**Что это значит для пациентов.** Обращение к Google при входе сообщает ему,
что человек пользуется `polypsy.ink` — то есть посещает психологическое
отделение. Это ровно тот факт, который система в остальном бережёт: код
вместо имени в расписании, телефон не в списках, отдельное действие на его
показ. Поэтому вход через Google разумен для персонала и **не** предлагается
пациентам: учётную запись под кодом связать с Google нельзя вовсе, сервер
откажет.

### Что завести в Google

[console.cloud.google.com](https://console.cloud.google.com) → APIs & Services
→ Credentials → Create credentials → **OAuth client ID** → Web application.

| Поле | Значение |
|---|---|
| Authorized JavaScript origins | `https://polypsy.ink` |
| Authorized redirect URIs | `https://polypsy.ink/api/auth/google/callback` |

Адрес возврата должен совпасть посимвольно — расхождение даёт
`redirect_uri_mismatch`, и это самая частая ошибка здесь.

На экране согласия (OAuth consent screen) достаточно областей `openid`,
`email`, `profile`: имя и почта — всё, что нужно, чтобы понять, кто вошёл.

### Что вписать на сервере

```sh
cd /opt/quizzy
cat >> .env.docker <<'EOF'
GOOGLE_CLIENT_ID=<из консоли Google>
GOOGLE_CLIENT_SECRET=<из консоли Google>
GOOGLE_REDIRECT_URI=https://polypsy.ink/api/auth/google/callback
# Домены почты через запятую. Пусто — любые; для персонала лучше указать
GOOGLE_ALLOWED_DOMAINS=
EOF
docker compose --env-file .env.docker up -d api
```

### Как этим пользоваться

Google **не создаёт** учётных записей: роль и область видимости назначает
человек, а не внешний поставщик входа. Поэтому порядок такой:

1. администратор заводит сотрудника обычным способом;
2. сотрудник входит паролем;
3. в панели учётной записи слева нажимает «Привязать Google»;
4. дальше может входить любым из двух способов.

Отвязать можно там же и в любой момент — в том числе если вход через Google
из настроек убрали.

Связывание и отвязывание попадают в журнал наравне со сменой пароля: это
выдача второго ключа от учётной записи, а не настройка удобства.
