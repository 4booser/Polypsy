# Развёртывание на VPS

Один сервер — одно учреждение. Колонок арендатора в таблицах нет, и это
решение волны 8: цена перенесена из схемы в эксплуатацию и платится явно.

## Что нужно от сервера

| | Минимум | Рекомендуемо | Почему |
|---|---|---|---|
| Ядра | 2 | **4** | Расшифровка часового приёма занимает минуты и должна идти, не задевая консоль |
| Память | 2 ГБ | **8 ГБ** | Postgres, приложение и модель `small` в памяти одновременно |
| Диск | 20 ГБ | **80 ГБ** | Записи приёмов: час разговора ≈ 30 МБ в сжатом виде |
| ОС | Debian 12 / Ubuntu 24.04 LTS | **Debian 12** | `vps-setup.sh` ставит ufw, fail2ban и обновления безопасности только на apt-системах; на Arch их нет, и сервер стоял без обновлений |
| Диск | NVMe/SSD | | снимки базы и расшифровка — дисковые |
| Архитектура | x86-64 | | образы собираются только под amd64; на ARM-сервере выкатка не встанет |
| Сеть | IPv4 свой, 1 Гбит | | A-запись домена на этот адрес |

Поставщик — любой с датацентром в ЕС (Франкфурт, Варшава, Хельсинки — 20–40 мс
до Украины). Снимки диска у поставщика — плюс, но не замена своих копий:
внешняя копия должна лежать у **другого** поставщика (см. «Внешняя копия»).
Сейчас (октябрь 2026) база — 76 МБ, нагрузка около нуля: запас по ядрам и
памяти нужен расшифровке, а не консоли.

**Про расшифровку отдельно.** whisper.cpp на процессоре работает примерно со
скоростью разговора: часовой приём — около часа счёта на двух ядрах моделью
`small`. Восемь приёмов за день расшифровываются к утру следующего, и это
нормальный режим: стенограмма нужна к разбору, а не к концу приёма. Если
нужна быстрее — берите больше ядер, а не меньшую модель: `tiny` и `base` на
украинском и русском дают текст, который приходится переписывать целиком.

## Первая установка

**Одной командой на чистом Debian 12** — `scripts/server-install.sh`: пакеты,
клон в `/opt/quizzy`, `vps-setup.sh` (Docker, защита
хоста, окружение, стек, первый администратор), служба и таймеры копий,
ключ для выкатки из GitHub Actions — и в конце печатает значения секретов
репозитория и список того, что сохранить вне сервера.

```sh
scp scripts/server-install.sh root@<сервер>:/root/
ssh root@<сервер> 'bash /root/server-install.sh polypsy.ink'
```

Повторный запуск доделывает недостающее и не трогает ключи, пароли и
фразы. Ниже — те же шаги по отдельности, если что-то нужно сделать руками.

Хранилище публичное, и клону ключ не нужен. Если его снова закроют, запускайте
установщик с `REPO=git@github.com:4booser/Polypsy.git`: он заведёт ключ на
чтение сам. Руками это делается так, и заводится ключ на самом сервере —
закрытая часть никуда не уезжает:

```sh
ssh-keygen -t ed25519 -f ~/.ssh/quizzy_deploy -N "" -C "quizzy@$(hostname)"
cat ~/.ssh/quizzy_deploy.pub
```

Открытую часть добавьте в репозиторий: Settings → Deploy keys → Add,
**без** права записи. И научите ssh ею пользоваться:

```sh
cat >> ~/.ssh/config <<'EOF'
Host github.com
  IdentityFile ~/.ssh/quizzy_deploy
  IdentitiesOnly yes
EOF
```

Дальше всё делает один скрипт:

```sh
git clone https://github.com/4booser/Polypsy.git /opt/quizzy
cd /opt/quizzy
sudo ./scripts/vps-setup.sh polypsy.ink
```

Он ставит Docker, заводит `.env.docker` со случайными паролями, поднимает
стек (из реестра, если в окружении задан `QUIZZY_IMAGE_PREFIX`, иначе собирает
на месте), **проверяет что политики строк действуют и шифрование включено** и
заводит первого администратора, печатая его пароль один раз.

Пароли генерируются алфавитом base64url. Это не придирка: они попадают в
строку подключения вида `postgres://user:ПАРОЛЬ@host/db`, а обычный base64
даёт «/» и «+» — первый обрывает адрес на месте пароля.

Скрипт идемпотентен и **не перегенерирует пароли** на повторном запуске.
Перегенерация `ENCRYPTION_KEY` на работающем экземпляре означала бы, что
все зашифрованные поля больше не читаются — ни ФИО, ни заключения.

### Если ставить руками

```sh
curl -fsSL https://get.docker.com | sh
cp .env.docker.example .env.docker   # и заполнить
```

Заполнить `.env.docker`. Три значения обязаны быть случайными и разными:

```sh
head -c 24 /dev/urandom | base64 | tr '+/' '-_' | tr -d '\n='   # POSTGRES_PASSWORD
head -c 24 /dev/urandom | base64 | tr '+/' '-_' | tr -d '\n='   # APP_DB_PASSWORD
head -c 32 /dev/urandom | base64   # JWT_SECRET
```

Пароли базы — алфавитом base64url (`tr '+/' '-_'`), как у `vps-setup.sh`:
они подставляются в адрес подключения как есть. С «/» из обычного base64
приложение не стартует; provision отказывает такому `APP_DB_PASSWORD`
заранее, а сервер — неразборчивому `DATABASE_URL`, не печатая пароля.

И отдельно — ключ шифрования полей. Без него сервер в production **не
стартует**: установка без ключа пишет ФИО, даты рождения, телефоны,
свободные ответы, заключения, заметки приёма и стенограммы открытым текстом
и ничем себя не выдаёт. Если экземпляр уже работает без ключа — добавьте
ключ и прогоните `bun run --cwd apps/api db:encrypt`: старые открытые
значения читаются и после включения шифрования, новые пишутся
зашифрованными.

```sh
echo "v1:$(head -c 32 /dev/urandom | base64)"   # ENCRYPTION_KEY
```

Ещё три секрета — свои, и совпадать ни с `JWT_SECRET`, ни между собой они не
должны (сервер это проверяет и отказывается стартовать):

```sh
head -c 32 /dev/urandom | base64   # PHONE_INDEX_SECRET — слепой индекс телефона
head -c 32 /dev/urandom | base64   # EXPORT_SECRET — коды субъекта в выгрузках
head -c 32 /dev/urandom | base64   # SEARCH_INDEX_SECRET — слепой индекс поиска по записям
```

Почему не один на всё: `JWT_SECRET` меняют при любом подозрении на утечку, и
с общим значением такая ротация молча ломала бы дедупликацию телефонов,
склейку лонгитюда в выгрузках и поиск по записям приёма (200 с пустым
списком при целых записях); а сама утечка секрета подписи позволяла бы
восстановить телефоны из дампа перебором. Смена `PHONE_INDEX_SECRET`
требует пересчёта: `bun run --cwd apps/api db:reindex-phones`. Смена
`EXPORT_SECRET` меняет коды субъекта — датасеты, выгруженные до неё, с
новыми не склеятся. Смена `SEARCH_INDEX_SECRET` замечается сама: при старте
api сравнивает отпечаток секрета с журналом переиндексаций (`security_jobs`
вида `search_reindex`) и пересобирает индекс в фоне; пока идёт пересборка,
поиск по старым записям пуст — минуты. Руками:
`bun run --cwd apps/api search:reindex` — печатает число записей, отпечаток
секрета и номер задания.

Выкатка (`deploy.yml`) заводит недостающие `PHONE_INDEX_SECRET`,
`EXPORT_SECRET` и `SEARCH_INDEX_SECRET` на сервере сама и только при
отсутствии. Для `SEARCH_INDEX_SECRET` это и есть переход: индекс, построенный
на `JWT_SECRET`, первый же старт api пересобирает на новый секрет.

Ключ шифрования **не хранится в снимках базы** и не восстанавливается. Его
потеря означает потерю всех зашифрованных полей — положите копию туда же,
где храните доступы к серверу.

Дальше:

```sh
# 4. Запуск. Первый занимает время: собираются образы и качается модель
docker compose --env-file .env.docker up -d --build

# 5. Первый администратор
docker compose --env-file .env.docker exec api bun apps/api/src/install.ts
```

Ещё один суперадминистратор — на уже работающем экземпляре (установщик его
не заведёт: он создаёт только первого). Пароль рождается на сервере и
печатается один раз в этом терминале:

```sh
docker compose --env-file .env.docker exec api \
  bun apps/api/src/addSuperadmin.ts --email you@example.com --first Имя --last Фамилия
```

## Переезд на другой сервер

Весь перенос делает `scripts/server-move.sh`. Он запускается с машины
администратора, у которой есть ssh на оба сервера. Старый работает до
последнего шага, а простой — только от заморозки до смены DNS: минуты
переноса и TTL записи.

**До начала:**

- Эти скрипты должны быть в `main`: новый сервер клонирует его. Новый выпуск
  ради переезда не нужен, и совмещать их не стоит: новый сервер встаёт на той
  же версии образов, что старый.
- Новых выпусков на время переезда не выкатывать.
- `ENCRYPTION_KEY` и `BACKUP_PASSPHRASE` — в менеджере паролей, вне сервера.
- Новый сервер — Debian 12, x86-64, ключ администратора у root.
- Внешнюю копию лучше завести заранее (см. «Внешняя копия»): пока её нет, все
  копии базы лежат только на старом диске. Сценарий переносит их с собой.

```sh
export OLD=root@<старый> NEW=root@<новый>

scripts/server-move.sh check     # обзор обоих серверов, ничего не меняет
scripts/server-move.sh install   # новый сервер: окружение старого, образы той же версии
scripts/server-move.sh rehearse  # проба: копия данных на новый, старый работает
```

`check` называет препятствия: архитектуру, место, закрытые исходящие порты (в
том числе SMTP — поставщики часто закрывают его на новых счетах), отсутствие
внешней копии, задания cron и правки, которых на новом не будет. `install`
кладёт окружение старого сервера целиком и зовёт `server-install.sh`; пароль
администратора в его выводе не нужен, база будет заменена. Секреты и DNS из
его итога пока не трогать.

После `rehearse` новый сервер поднят на копии, с настоящим сертификатом, но
без планировщика, почты и Telegram. Проверка:

```sh
curl --resolve polypsy.ink:443:<новый ip> https://polypsy.ink/health/ready
```

В браузере — строка `<новый ip> polypsy.ink` в `/etc/hosts`. На копии только
смотреть: пуши с действий в консоли уходят настоящим людям. Закончив, строку
убрать. Пробу можно повторять сколько угодно: база каждый раз заливается в
заново созданную.

**Переключение.** В тихий час, когда никто не ведёт приём. Мобилка и кабинет
пациента переждут простой сами (502 для них — временный отказ, сдача ждёт в
очереди), несохранённое в консоли — нет.

1. Заранее, не меньше чем за прежний TTL (сейчас 30 минут): TTL записей `@` и
   `www` — 300 секунд.
2. `scripts/server-move.sh cutover`. Он спросит домен, остановит `api` и
   `transcriber` на старом, снимет финальный снимок, перенесёт его с записями
   приёмов, сертификатами и копиями базы, сверит число строк и последнюю запись
   журнала и запустит новый в полную работу. Несовпадение останавливает его до
   запуска; тогда `scripts/server-move.sh rollback`.
3. A-записи `@` и `www` — на новый адрес. Если появится AAAA, менять и её.
4. `scripts/server-move.sh secrets` — `VPS_HOST`, `VPS_USER`, `VPS_PATH`,
   `VPS_SSH_KEY` и `VPS_KNOWN_HOSTS` смотрят на новый сервер. Раньше не надо:
   выкатка на пробный сервер сняла бы с него тишину.

Режим обслуживания перед снимком не включать: он лежит в базе и приедет на
новый включённым.

Выкатка в окне простоя не нужна: образы на новом уже те же, а её прогон с
тестами занимает 40–50 минут.

**Откат** — `scripts/server-move.sh rollback`: новый останавливается, старый
поднимается. Работает, пока домен не переключён; после этого записи на новом
уже настоящие, и сценарий откажет. Запись `FORCE_ROLLBACK=1` — для тех, кто
осознанно их теряет.

**После:**

1. Обслуживание: `backup-status`, `rls-check`, `audit-verify`, `backup-verify`.
2. Техпанель, «Сповіщення»: «Відправити тестове» в Telegram и на почту.
3. Вход через Google, если он включён: адрес тот же, менять
   ничего не надо.
4. Следующий выпуск пройдёт уже на новый сервер; первая выкатка — проверка
   всей цепочки. Проверить её раньше можно запуском «Выкатка» на текущем теге.
5. Старый выключить через сутки, снести через неделю. У поставщика удалить
   снимки диска: на них база и ключи. В Deploy keys репозитория удалить ключ
   старого сервера.

Проверка самого сценария на двух контейнерах —
`scripts/test/server-move-roundtrip.sh`.

## Домен и TLS

До покупки домена всё работает по IP на `:80`. После — впишите домен в
`SITE_ADDRESS` и перезапустите консоль:

```sh
# A-запись домена должна указывать на IP сервера ДО этого шага:
# сертификат выдаётся по факту владения, и без записи выдача не пройдёт
docker compose --env-file .env.docker up -d web
```

Caddy сам получит сертификат Let's Encrypt и будет его продлевать. Порты 80
и 443 должны быть открыты — 80 нужен и после перехода на https, для
продления.

Заодно впишите тот же адрес в `CORS_ORIGINS` и `CONSOLE_URL`.

## Выкатка обновлений

Настраивается один раз, дальше — тег в git.

**Секреты репозитория** (Settings → Secrets → Actions):

| Секрет | Что это |
|---|---|
| `VPS_HOST` | адрес сервера |
| `VPS_USER` | пользователь с правом запускать docker |
| `VPS_PATH` | каталог установки, например `/opt/quizzy` |
| `VPS_SSH_KEY` | закрытый ключ для входа (заведите отдельный, только для выкатки) |
| `VPS_KNOWN_HOSTS` | вывод `ssh-keyscan <host>`, снятый один раз с доверенной машины |
| `SITE_ADDRESS` | домен консоли — по нему проверяется, что выкатка удалась |
| `ACME_EMAIL` | почта учётной записи Let's Encrypt: выкатка кладёт её в `.env.docker` |

`VPS_KNOWN_HOSTS` берётся из секрета, а не снимается с сервера в момент
выкатки: `ssh-keyscan` на живом соединении принимает любой ключ, включая
подменённый, и проверка превращается в её видимость.

На сервере в `.env.docker` добавьте:

```
QUIZZY_IMAGE_PREFIX=ghcr.io/4booser/polypsy
QUIZZY_VERSION=latest
```

Образы публичные, постоянный вход сервера в реестр не нужен; выкатка на время
прогона входит сама, токеном прогона.

Дальше выкатка — это:

```sh
git tag v1.2.0 && git push origin v1.2.0
```

Порядок в выкатке: тесты → сборка образов → **снимок базы** → миграции и
перезапуск → проверка, что приложение отвечает. Снимок именно перед
миграциями: переключением тега схема назад не откатывается, и старый образ
на новую схему не встанет.

Снимок выкатки лежит в своём каталоге — `$BACKUP_DIR/predeploy/`, хранятся
10 последних. В ротацию суточных, недельных и месячных копий он не входит:
окружение выкатка берёт у службы `quizzy-backup`, а снимает
`scripts/backup.sh` с `BACKUP_KIND=predeploy`. Прежде она запускала саму
службу, и несколько выкаток за день вытесняли копии прошлых дней.

### История выкаток и откат

Выкатка кладёт в `.env.docker` кроме версии ещё коммит, того, кто её
запустил, ссылку на прогон CI и репозиторий (`QUIZZY_COMMIT`,
`QUIZZY_DEPLOYED_BY`, `QUIZZY_RUN_URL`, `QUIZZY_REPO`). `docker-compose.yml`
передаёт их в контейнер api, и API при старте записывает выпуск в историю —
раздел «Випуски» техпанели. Руками их не пишут. Доехали ли они до
контейнера, выкатка проверяет сама (шаг «Настройка доехала до контейнера»).
При `QUIZZY_VERSION=latest` или `local` выпуск не записывается: плавающий тег
не называет никакого кода.

Откат на прежний тег — это новая выкатка старого тега поверх той же базы:
Actions → «Выкатка» → Run workflow → в поле `ref` вписать тег. **Миграции
при этом остаются** — раздел «Випуски» перед кнопкой показывает, какие
именно, и если среди них есть несовместимые со старым кодом, путь один:
восстановление из снимка, сделанного перед выкаткой.

Чтобы кнопка «Відкотити» в техпанели запускала выкатку сама, а не вела на
страницу GitHub, впишите на сервере в `.env.docker` `GITHUB_DISPATCH_TOKEN`:
fine-grained токен только на этот репозиторий с одним правом — Actions: read
and write. Запуск из панели доступен только с правом «Керувати роботою
системи» (ops.manage) и пишется в журнал; сам токен панель не показывает.

## Резервные копии

`scripts/backup.sh` кладёт снимок и проверяет, что он читается. Раз в сутки:

```sh
sudo tee /etc/cron.d/quizzy-backup <<'EOF'
0 3 * * * root cd /opt/quizzy && ./scripts/backup.sh >> /var/log/quizzy-backup.log 2>&1
EOF
```

**Снимок без проверки восстановлением — это не резервная копия, а надежда.**
Раз в месяц прогоняйте `scripts/verify-backup.sh`: он поднимает копию в
отдельной базе, проверяет, что схема и данные на месте, и пересчитывает
журнал доступа образом api — поэтому запускается из каталога установки
(`/opt/quizzy`). По расписанию это делает обслуживание (`maintenance.yml`,
1-го числа).

### Внешняя копия

Копии лежат на том же сервере, что и база: отказ диска или потеря учётной
записи у поставщика уносит и данные, и копии. Внешняя копия — в
S3-совместимом хранилище **другого** поставщика (Backblaze B2, Cloudflare
R2). Уходит уже зашифрованный файл, хранилище видит только шифротекст.
Делает это `scripts/offsite.sh`, его зовёт `backup.sh` после каждого
снимка; без настройки он молча пропускается.

Отказ внешней копии не отменяет местную, ротацию и выкатку: `backup.sh`
пишет в журнал «внешняя копия не легла» и шлёт оповещение в канал техпанели
(`scripts/ops-alert.sh`: через приложение, иначе прямо в Telegram из
`.env.docker`). Отказ самих служб `quizzy-backup` и `quizzy-verify` — тоже
оповещение: `OnFailure=quizzy-alert@%n.service` (заводит `server-install.sh`).

1. Заведите корзину и ключ доступа **только к ней**, с правами на чтение и
   запись, без удаления. Включите в корзине правило хранения (lifecycle):
   удалять объекты старше 400 дней — ротацию снаружи делает оно, а не
   скрипт.
2. Впишите в окружение службы копий (`/root/quizzy-backup.env`):

   ```
   OFFSITE_URL=https://<account>.r2.cloudflarestorage.com/<bucket>   # R2
   OFFSITE_URL=https://s3.<region>.backblazeb2.com/<bucket>          # B2
   OFFSITE_KEY_ID=…
   OFFSITE_SECRET=…
   OFFSITE_REGION=auto        # R2: auto; B2: область из адреса, например us-west-004
   ```
3. Проверьте: `systemctl start quizzy-backup.service`, затем в журнале
   службы — строка «внешняя копия: daily/…». Сверка всех копий —
   обслуживание, действие `offsite-status`, или на сервере
   `scripts/offsite.sh check` с тем же окружением.

Отдельно от базы копируйте:

- `ENCRYPTION_KEY` — без него зашифрованные поля не прочитать ничем;
- том `recordings` — записи приёмов лежат файлами, в снимке базы их нет.

## Что проверить после первого запуска

```sh
# 1. Политики строк действуют. В журнале должно быть «rls active».
docker compose --env-file .env.docker logs api | grep rls

# 2. Шифрование включено. Без ключа процесс не стартует вовсе —
#    значит «api поднялся» и есть ответ; проверяем, что ключ задан.
grep -c '^ENCRYPTION_KEY=v' .env.docker

# 3. Расшифровщик нашёл модель.
docker compose --env-file .env.docker logs transcriber | tail -3
```

Первый пункт — самый важный и самый незаметный. Приложение обязано
подключаться к базе ролью `quizzy_app`, которая таблицами не владеет:
владелец в PostgreSQL обходит политики строк, и с ним все сорок семь политик
остаются на месте, но каждый видит всё. Отличить это от исправной работы
нельзя ничем — запросы отрабатывают, экраны рисуются. Поэтому сервер в
production такой запуск не принимает и говорит, что делать.

## Вход через Google

Дополнительный способ входа, а не замена паролю. Пока в окружении пусто —
способа просто нет, и кнопка не рисуется.

**Что это значит для пациентов.** Обращение к Google при входе сообщает ему,
что человек пользуется `polypsy.ink` — то есть посещает психологическое
отделение. Это ровно тот факт, который система в остальном бережёт: код
вместо имени в расписании, телефон не в списках, отдельное действие на его
показ. Поэтому вход через Google разумен для персонала и **не** предлагается
пациентам: учётную запись под кодом связать с Google нельзя вовсе, сервер
откажет.

### Что завести в Google

[console.cloud.google.com](https://console.cloud.google.com) → APIs & Services
→ Credentials → Create credentials → **OAuth client ID** → Web application.

| Поле | Значение |
|---|---|
| Authorized JavaScript origins | `https://polypsy.ink` |
| Authorized redirect URIs | `https://polypsy.ink/api/auth/google/callback` |

Адрес возврата должен совпасть посимвольно — расхождение даёт
`redirect_uri_mismatch`, и это самая частая ошибка здесь.

На экране согласия (OAuth consent screen) достаточно областей `openid`,
`email`, `profile`: имя и почта — всё, что нужно, чтобы понять, кто вошёл.

### Что вписать на сервере

```sh
cd /opt/quizzy
cat >> .env.docker <<'EOF'
GOOGLE_CLIENT_ID=<из консоли Google>
GOOGLE_CLIENT_SECRET=<из консоли Google>
GOOGLE_REDIRECT_URI=https://polypsy.ink/api/auth/google/callback
# Домены почты через запятую. Пусто — любые; для персонала лучше указать
GOOGLE_ALLOWED_DOMAINS=
EOF
docker compose --env-file .env.docker up -d api
```

### Как этим пользоваться

Google **не создаёт** учётных записей: роль и область видимости назначает
человек, а не внешний поставщик входа. Поэтому порядок такой:

1. администратор заводит сотрудника обычным способом;
2. сотрудник входит паролем;
3. в панели учётной записи слева нажимает «Привязать Google»;
4. дальше может входить любым из двух способов.

Отвязать можно там же и в любой момент — в том числе если вход через Google
из настроек убрали.

Связывание и отвязывание попадают в журнал наравне со сменой пароля: это
выдача второго ключа от учётной записи, а не настройка удобства.
