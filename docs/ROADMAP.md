## Контекст

Quizzy — система психодиагностики для военно-медицинского учреждения: API (Bun + Hono +
Drizzle + PostgreSQL 16), веб-консоль (Vite + React 19), мобильное приложение (Expo SDK 57),
общий пакет с движком подсчёта. ~17k строк TS. Уже реализовано: версионирование методик,
ключевой подсчёт (K-коррекция, T-баллы, стены, шкалы достоверности), группы и скоупинг
админов (`lib/scope.ts`), журнал доступа включая чтения, тревоги риска с эскалацией,
потоковая телеметрия ответов, психометрия (альфа Кронбаха, item-total), сравнение когорт,
корреляции, SPSS-экспорт, батареи со строгим порядком (серверная проверка), расписания
повторов с идемпотентным исполнителем, печатные бланки и ключи, 4 реальные методики.

Решения пользователя при планировании:
- **Развёртывание: облако/VPS** — можно email/push и внешний мониторинг; выше требования к защите.
- **Приоритет после фундамента: масштаб и полировка** (киоск, приглашения, i18n, рефакторинг).
- **Защита данных: разумный максимум** — всё, что возможно без внешних аудиторов.

Сквозной принцип всей карты: каждый новый фоновый процесс — по образцу `lib/scheduler.ts`
(идемпотентный тик + журнал запусков), каждое действие — в `AuditAction` (`lib/audit.ts`),
каждая выборка — через `surveyScopeFilter`/`assertGroupAccess`, каждый расчёт — чистой
функцией в `packages/shared` с золотым тестом.

## Найденные дефекты — ✅ все 8 закрыты

1. **Репозиторий не под git** — ни одного коммита. Потеря диска = потеря всего проекта.
2. **Дыра авторизации:** `apps/api/src/routes/access.ts:129` — `GET /api/access/patients`
   отдаёт ВСЕХ пациентов (имя, email, подразделение) любому групповому админу без
   фильтра `accessibleGroupIds` и без аудита. Патч: фильтровать по доступным группам + журнал.
3. **Неверное действие в журнале:** `users.ts` пишет `"user.create"` при смене роли
   (`PATCH /:id/role`) — завести `"user.role_change"`.
4. **Мёртвое объявление** `"response.draft"` в `AuditAction` — нигде не эмитится; убрать
   или начать логировать.
5. **CORS `*`** при токенах в localStorage — сузить до allowlist из env.
6. **`GET /health` не проверяет БД** — вернёт ok при упавшем Postgres; добавить `select 1`,
   разделить liveness/readiness. Плюс: «планировщик тикал < 2 ч назад» по `schedule_runs`.
7. **Stop-колбэк планировщика выбрасывается** (`index.ts:59`) — сохранить и вызывать при
   SIGTERM.
8. **Нет смены/сброса пароля вообще** — заблокированного пользователя чинят руками в БД.

переключении. Данные посева совпадут, забытая подпись — останется. Он сразу
нашёл два десятка пропущенных строк в многострочных подсказках.

### 1.7 E2E-смоук (M) — ✅
Playwright против настоящего стенда: собранная консоль (`vite preview`, не
dev-сервер — в проде отдаётся именно сборка) + живой API + отдельная база
`quizzy_e2e`, пересоздаваемая перед прогоном. Порты 3199/4199, чтобы стенд не
дрался с запущенным dev.

Что проверяется:
- **вход** — отказ по неверному паролю, живучесть сессии после перезагрузки,
  скрытая администрация у группового админа;
- **клинический контур целиком** — тревоги → пациент → сводка → выписать
  направление → принять → завершить → пропадает из открытых, находится с
  фильтром. Проверяется и запрет перескока через ступень: кнопки «Завершено»
  на выписанном направлении просто нет;
- **скоуп** — списки пациентов у двух групповых админов не совпадают;
- **конструктор** — массовая вставка пунктов текстом, проверка структуры,
  публикация, методика в списке;
- **доступность** — axe (WCAG 2.1 AA) на четырёх экранах × две темы.

Файлы `*.e2e.ts`, а не `*.spec.ts`: иначе `bun test` в корне подхватывает их
и падает на импорте `@playwright/test`.

Найдено при внедрении: `db:reset` был сломан с момента написания —
`migrate.ts` закрывает общий пул, и посев в том же процессе писал в мёртвое
соединение; шесть нарушений контраста в обеих темах (приглушённый текст,
активный пункт меню, git-sha под полупрозрачностью).

### 2.1 Уведомления о тревогах (M) — ✅ (email+эскалация; push — позже)

- Эскалация: `alertEscalateMinutes` уже в схеме — тик по образцу планировщика (1–5 мин)

### 2.2 Офлайн-режим мобилки (L) — ✅
Локальная БД (expo-sqlite) — источник истины: кэш полной версии назначенной методики
(контент версии иммутабелен — версионирование это гарантирует), локальный черновик,
очередь мутаций (ответы, события, сдача) с ретраями/backoff; NetInfo → синк; конфликтов
почти нет (append-only, один пациент — одно устройство). Тайминги пишутся локально в
момент событий — сервер уже принимает их как есть. Идемпотентный upsert черновика по
клиентскому id. Индикатор «не синхронизировано: N», запрет логаута при непустой очереди.
`computeProfile` в shared — завершение показывается офлайн; при синке серверный пересчёт
сверяется и расхождения логируются (их быть не должно — общий код).

### 2.3 Заключения (M) — ✅ (печать через браузер; серверный PDF — позже)
- Таблица `conclusions` (responseId, текст специалиста, статус draft/signed, версии,

### Снятие методики с использования — ✅

`DELETE /api/surveys/:id` уничтожал по внешним ключам все прохождения, баллы,
тревоги и назначения по методике — клиническую историю живых людей,
необратимо и без подтверждения. Теперь метод снимает методику с
использования: `archivedAt` + кто снял.

Снятая методика исчезает из всего, что смотрит **вперёд** — списки, выдача
доступа, батареи, киоск, расписания, новые прохождения и черновики — и
остаётся во всём, что смотрит **назад**: карта пациента, аналитика, журнал.
Дыры в клинических записях недопустимы: методику вывели из оборота, но
человек её проходил, и это остаётся фактом.

Точка проверки одна на все пути выдачи (`assertSurveysInUse`), иначе шесть
отдельных проверок неизбежно разъедутся. Автоматические выдачи — расписание,
каскад, приглашение — снятую методику молча пропускают и выдают остальные:
расписание работает в усечённом виде, а не встаёт целиком.

Физическое удаление — только с сервера: `bun run survey:purge <id>`. Требует,
чтобы методика уже была снята (между решением и необратимым действием должен
быть промежуток), печатает, сколько прохождений и тревог будет уничтожено, и
требует повторить точное название. Запись в журнал делается ДО удаления —
журнал защищён хэш-цепочкой и переживёт саму методику.

Заодно: `"archived"` убран из перечисления `status`. Значение никогда не
выставлялось и нигде не проверялось, но выглядело рабочим — рано или поздно
им бы «сняли» методику, ничего при этом не запретив.

### Каскады удаления — ✅

Ревизия всех внешних ключей после истории с методиками: где ещё удаление
одной строки уносит клинические данные.

- **Группа** удаляла батареи (`batteries.group_id` каскадный), а с ними
  историю назначений, расписания и сеансы киоска. Методики при этом
  получали `group_id = null` и по правилам `scope.ts` превращались в личные
  черновики создателя — остальные админы группы молча теряли доступ.
  Теперь непустая группа не удаляется.
- **Батарея** проверяла только *открытые* назначения. Завершённое
  назначение — это запись о том, что человек реально проходил набор; каскад
  стирал её, и в карте оставалось прохождение без объяснения, откуда оно.
  Теперь удаляется только батарея, которая ни разу не назначалась.
- **Учётная запись** была связана с созданными ею методиками каскадом:
  одна ручная чистка учётки в `psql` уносила методики вместе со всеми
  прохождениями. Шесть авторских связей (`createdBy` у методик, групп,
  батарей, расписаний, приглашений, сеансов) переведены на `RESTRICT`.
  Колонки `userId` остались каскадными — согласия, назначения и токены
  принадлежат самому человеку и уходят вместе с ним.

Полная карта «что уходит следом» — в RUNBOOK: при ручной работе в psql
защиты приложения не работают.

# Расширение плана: этапы 5–8 (медицинская аналитика и клинический контур)

Составлено 2026-08-26 после закрытия этапов 0–2 и половины этапа 4. Ядро
расширения — два принципа, которых не хватает нынешней аналитике, и четыре
этапа, которые на них строятся.

## Сквозные принципы

### П-1. Стратификация по полу и возрасту — везде

Ни одна метрика не существует «в среднем по больнице»: тревожность женщин
25–34 и мужчин 45+ — разные распределения, и усреднение прячет обе группы.
Правило для ВСЕХ новых и существующих срезов аналитики:

- каждая метрика фасетируется по **полу × возрастной полосе**
  (до 25 / 25–34 / 35–44 / 45+ — полосы уже стандартизованы в системе:
  сравнение когорт, SPSS-экспорт);
- возраст всегда «на момент обследования» (ageAt), не текущий;
- **подавление малых ячеек**: страта с n < 5 не показывается и не
  выгружается («< 5» вместо числа) — стандарт медицинской статистики против
  реидентификации; порог конфигурируем (`SMALL_CELL_FLOOR`);
- при сравнении групп с разной половозрастной структурой показатели
  дополнительно **стандартизуются** (см. 5.5) — иначе «рота А тревожнее
  роты Б» может означать лишь «рота А моложе».

### П-2. Замкнутый клинический контур

Скрининг без верификации — генератор непроверенных чисел. Каждая тревога и
каждый повышенный балл должны получать клинический исход (подтверждён /
не подтверждён / направлен), и эти исходы — сырьё для калибровки порогов
(5.7): система учится на решениях своих же психологов.

## Этап 5 — Медицинская аналитика второго порядка

### 5.1 Стратифицированные срезы — ✅

**Зачем.** Сейчас распределения, статистика пунктов и надёжность считаются
по всей выборке; половые различия норм уже признаны системой (T-баллы по
полу), а аналитика этого не отражает.

**Что.** В аналитике методики — переключатель фасета «все / пол / возраст /
пол×возраст»:
- распределения баллов и интерпретационных полос — по стратам;
- статистика пунктов (среднее, доля «да») — по стратам;
- воронка доходимости — по стратам (женщины бросают на пункте 34?);
- везде подавление ячеек n < `SMALL_CELL_FLOOR`.

**Реализация.** Расширить `routes/analytics.ts` параметром `facet`;
считать в SQL (`GROUP BY sex, age_band`), возрастную полосу — вычисляемым
выражением от расшифрованной даты рождения… **важно**: birthDate шифрован,
SQL-группировка по нему невозможна → добавить в `responses` снэпшот
`respondentAgeBand` и `respondentSex` **на момент сдачи** (заполняется в
persistSubmission; заодно это исторически честнее — пол/возраст фиксируются
такими, какими были при обследовании). Бэкфилл по расшифровке в JS.

**Тесты.** Страта n<5 подавлена; сумма страт = целому; полоса от ageAt на
момент сдачи, не текущего.

### 5.2 DIF по полу, возрасту и языку — ✅

**Зачем.** Пункт «я часто плачу» у мужчин и женщин с одинаковым уровнем
депрессии работает по-разному — суммарный балл смещается не из-за состояния,
а из-за формулировки. Для методик, перенесённых из пособий 1980–2010-х, это
не гипотеза, а ожидание.

**Метод.** Mantel–Haenszel: стратификация по суммарному баллу шкалы
(4–5 страт), в каждой — таблица 2×2 (группа × ответ по ключу);
χ²MH + общий отношение шансов αMH; ΔMH = −2.35·ln(αMH);
классификация ETS: |ΔMH| < 1 — A (нет DIF), 1–1.5 — B (умеренный),
> 1.5 при значимости — C (выраженный).

**Guard-ы (главное).** MH при выборках < 200 на группу ненадёжен
(Fidalgo 2004): при n < 200 — помечать «предварительно», использовать
α = 0.2 вместо 0.05; при n < 50 в любой группе — не считать вовсе.
DIF ≠ приговор пункту: класс C — сигнал на клинический разбор, не
автоматическое исключение из ключа.

**Реализация.** `packages/shared/src/dif.ts` — чистая функция
`mantelHaenszel(strata: {a,b,c,d}[]): {chi2, alphaMH, deltaMH, class}` с
золотым тестом на числовом примере, посчитанном руками. В API — расчёт по
полу и по возрастным полосам (референс — модальная группа) на вкладке
«Пункты» аналитики; в UI — колонка DIF с классами и подсказкой «что это
значит». Отдельно: **DIF по языку предъявления** (см. 7.4) — для двуязычной
системы это уникально важный разрез.

### 5.3 Перцентильные карты по возрасту — ✅

**Зачем.** Норма «одна на всех взрослых» из пособия скрывает возрастной
градиент. Формат врачам знаком по картам роста детей: кривые P10/P25/P50/
P75/P90 по возрасту, точка пациента — на фоне кривых его пола.

**Метод.** Скользящее возрастное окно ±5 лет (минимум 30 наблюдений в окне,
иначе окно расширяется до достижения минимума; честная пометка ширины окна);
квантили по скорректированному сырому баллу. Никакой экстраполяции за
пределы наблюдаемых возрастов.

**Реализация.** Эндпоинт percentile-map в norms-модуле; кривые — линии в
существующем LineChart; страница «Локальные нормы» получает вторую вкладку
«Возрастные кривые». Точка конкретного пациента — в его динамике.

### 5.4 Инвариантность надёжности — ✅

α Кронбаха отдельно по полу и полосам (уже есть машинерия reliabilityOf);
доверительный интервал Фельдта; предупреждение в аналитике при
Δα > 0.10 между группами: «шкала измеряет женщин надёжнее, чем мужчин —
сравнение их баллов менее точно, чем кажется».

### 5.5 Возрастно-половая стандартизация — ✅

**Зачем.** «Рота связи тревожнее штаба» — а рота связи на 10 лет моложе.
Прямая стандартизация: стандарт — половозрастная структура всего учреждения;
для каждого подразделения доля высокого риска пересчитывается «как если бы
структура была стандартной»: `Σ (rate_страта × вес_страта_стандарта)`.

**Реализация.** В сравнении когорт (`routes/comparison.ts`) — вторая колонка
«стандартизовано»; **явный флаг, когда стандартизация меняет порядок
групп** — это самый важный сигнал («сырая разница объяснялась возрастом»).
Чистая функция `directStandardize()` в стат-ядре (8.2) с золотым тестом.

### 5.6 Эпиднадзор: контрольные карты — ✅

**Зачем.** Всплеск доли высокого риска в конкретной роте должен быть виден
на неделе всплеска, а не в квартальном отчёте.

**Метод.** p-карта по неделям (доля прохождений с полосой severe/moderate),
контрольные пределы ±3σ от скользящего базового уровня; для малых
подразделений — EWMA (λ=0.2), устойчивее к малым n. Сигналы: выход за
предел; 8 точек по одну сторону центра (правила Western Electric).

**Реализация.** Страница «Надзор» (или вкладка Сводки): карта на
подразделение × методику; сигнал создаёт запись типа тревоги
(`surveillance_signals`) и письмо админам группы через существующий
рассыльщик. Стандартизованные доли (5.5) — как опция. Стат-ядро:
`pChart()`, `ewma()` с тестами.

### 5.7 ROC-калибровка порогов — ✅

**Зачем.** Пороги пособий получены на чужих популяциях. Когда накопятся
верифицированные исходы (6.1), система может честно ответить: «порог 0.38
у нас даёт чувствительность 0.71 и специфичность 0.83; порог 0.31 —
0.86/0.74».

**Метод.** ROC по (балл, исход подтверждения); AUC; Youden J для
кандидатного порога; PPV/NPV при текущей базовой частоте. **Всё —
стратифицированно по полу** (пороги, как и нормы, могут различаться).
Guard-ы: минимум 30 подтверждённых и 30 отвергнутых исходов на страту;
доверительные интервалы (bootstrap); кандидатный порог публикуется как
интерпретационная полоса новой версии — тем же механизмом, что локальные
нормы, с источником «калибровка по N исходам».

### 5.8 Мониторинг PPV — ✅

Из исходов тревог: доля подтверждённых по методике/месяцу — на Сводке.
Падение PPV — ранний признак дрейфа выборки или усталости персонала от
ложных тревог (alarm fatigue) — то, из-за чего скрининги умирают.

## Этап 6 — Замыкание клинического контура

### 6.1 Исход тревоги — ✅

При подтверждении тревоги специалист выбирает исход: «подтверждена /
не подтверждена / требует наблюдения» + короткий комментарий. Одно поле в
существующем acknowledge — а открывает ROC, PPV и обучение порогов.
Существующие подтверждённые тревоги остаются без исхода (честный null).

### 6.2 Каскадные назначения — ✅

Правило на методике: «полоса ≥ X по шкале Y → автоназначить методику/батарею
Z» (скрининг → углублённая диагностика). Исполняется в persistSubmission
после подсчёта; назначение помечено «каскад от <методика>»; журналируется.
Guard: каскад назначает, но никогда не интерпретирует; циклы каскадов
запрещены валидацией правила.

### 6.3 Протоколы наблюдения — ✅

«Высокий риск → повтор через 7 дней, затем 30» — протокол на полосе
интерпретации. Реализация поверх расписаний: персональное одноразовое
расписание; пропуск повтора — эскалация существующим рассыльщиком.

### 6.4 Направления — ✅

Сущность `referrals`: куда (психиатр / стационар / амбулаторно / командиру /
иное), срочность (планово / срочно / немедленно), статус, основание, ответ
принимающей стороны, ссылки на прохождение и тревогу.

Статусы движутся **только вперёд**: `created → accepted → completed`,
отклонить можно на любом открытом шаге. Принятое направление нельзя
«отменить» задним числом — иначе разрыв контура маскируется правкой записи, а
не фиксируется как факт. Переход через ступень (`created → completed`)
отклоняется с 400.

Реестр открытых направлений — в консоли с бейджем в навигации: незакрытое
направление видно и через месяц. «Отправили к психиатру» без обратной связи —
самый частый разрыв клинического контура, и единственная защита от него —
чтобы запись не пропадала из вида.

### 6.5 Сводка для консилиума — ✅

`GET /api/referrals/summary/:userId` собирает в один ответ: паспортную часть
(пол, возраст, подразделение), по каждой методике — последние баллы шкал с
полосой интерпретации и меткой RCI (достоверный сдвиг / в пределах ошибки),
открытые тревоги, подписанные заключения, направления.

Новизна не в данных — они уже есть на семи экранах, — а в том, что их не надо
собирать за минуту до заседания. Печать даёт документ для подшивки: штамп
«сформирована ⟨дата⟩, ⟨кто⟩» появляется только на бумаге.

Чтение сводки — это чтение всей карты пациента, поэтому пишется в журнал как
`response.read` с пометкой `view: "case_summary"`. Скоуп тот же, что везде:
чужой групповой админ получает 404, а не пустую сводку.

## Этап 7 — Качество данных и психометрический контроль

### 7.1 Person-fit — ✅

Нормированные ошибки Гуттмана: у осмысленно отвечающего человека «тяжёлые»
пункты срабатывают только при высоком общем балле; хаотичный профиль или
«слишком идеальный» (симуляция/аграванация) — флаг качества рядом с
существующими too-fast/straight-line. Чистая функция в стат-ядре; флаг —
в качество прохождения и в отчёт (нейтрально: «паттерн ответов нетипичен»).

### 7.2 Дрейф выборки (PSI) — ✅

Population Stability Index распределения баллов месяц-к-месяцу
(PSI > 0.2 — существенный дрейф): предупреждение «выборка изменилась —
локальные нормы, посчитанные до <дата>, могут не подходить». Стат-ядро +
плашка на странице норм.

### 7.3 Отсев по стратам — ✅

Доходимость и пропуски пунктов по полу×возрасту (фасет 5.1 поверх воронки):
если женщины 45+ систематически бросают методику на середине — их данные
недопредставлены в нормах, и это надо ЗНАТЬ, а не догадываться.

### 7.4 Язык предъявления — ✅ (записывается, DIF по языку считается)

**Записывать язык прохождения** (`responses.lang` — какой язык был у
контента при сдаче; сейчас не фиксируется — слепое пятно двуязычной
системы). Дальше: сравнение α и средних uk vs ru, DIF по языку (5.2) —
«пункт 12 в русском переводе работает иначе, чем в украинском оригинале» —
прямой сигнал на правку перевода.

### 7.5 Тест-ретест ICC — ✅

ICC(2,1) по парам повторных замеров со стабильным интервалом (7–60 дней,
без событий тревоги между) — вторая оценка надёжности, независимая от
альфы. В стат-ядро + строка в аналитике шкалы.

## Что показало ревью

Не список пожеланий, а найденные дефекты — с указанием, чем каждый плох.

### Р.1 Экран тревог не выдерживает нагрузки — критично

397 тревог отрисованы плоским списком из 397 карточек: у каждой поле ввода и
три кнопки. Нет группировки, фильтра, сортировки и пагинации. Один человек с
пятью отмеченными пунктами даёт пять карточек подряд.

Это не косметика, а срыв клинического процесса: дежурный специалист на таком
экране не расставит приоритеты и не найдёт нужного человека. Чем больше
система работает, тем хуже она становится — обратная зависимость, недопустимая
для инструмента, который должен ловить суицидальный риск.

**Корень:** тревога смоделирована как событие по пункту, а не как случай по
человеку.

### Р.2 Списки без пагинации

`/api/alerts` отдаёт 318 КБ на 397 тревогах; `access/patients`, `dynamics`,
`audit`, `batteries` — тоже целиком. На пятикратном объёме это мегабайты в
одном ответе и подвисающий браузер. Курсорная пагинация есть только в журнале.

### Р.3 Интерфейс собран, но не спроектирован

Консоль работает и выглядит опрятно, но собрана из кусков, а не по системе:

- заголовки страниц оформлены двумя способами — часть через `PageHead`
  (с хлебными крошками и заголовком вкладки), часть сырым `<h1>`;
- поля дат — системные виджеты браузера, воткнутые под заголовком без
  выравнивания и группировки;
- кольцевая диаграмма занимает четверть экрана ради двух чисел;
- в боковой панели переключатель темы висит между навигацией и учётной
  записью без разделителя;
- одна контрольная точка адаптивности (900 px) — на планшете консоль
  разъезжается;
- 299 строк русского текста зашиты в разметку, хотя двуязычный механизм в

### Р.4 Ловушки навигации в мобильном приложении — исправлено по ходу

Вкладка «Аналитика» переадресовывала в отдельный стек **заменой**: возвращаться

перезапускать. Кнопка выхода добавлена; остальные экраны нужно пройти тем же

### Р.5 Наблюдаемости нет

Ни сбора ошибок, ни метрик, ни сквозного идентификатора запроса. При отказе на
работающей системе единственный источник — текстовый лог процесса. Разобрать
инцидент «у Иванова не сохранилось прохождение вчера вечером» по нему нельзя.

В консоли 30 страниц, сквозные проверки заходят на один адрес. Правка общего

## Этап 9 — Клинический контур под нагрузкой

Первое по важности: система должна оставаться пригодной, когда данных много.

### 9.1 Тревоги как случаи, а не события — ✅

Переход от «строка на сработавший пункт» к «карточка на человека».

**Данные.** Новая сущность `alert_cases`: `userId`, `surveyId`, `openedAt`,
`closedAt`, `severity` (максимум по входящим), `alertCount`, `status`,
`assignedTo`. Существующие `risk_alerts` становятся её содержимым — это
дешевле и честнее, чем плодить вторую истину: подробности «какой пункт
сработал» никуда не деваются, они уходят внутрь случая.

Открытие: первая тревога человека по методике заводит случай; последующие
в течение `caseWindowHours` (по умолчанию 72) прикрепляются к нему. Окно
настраивается на методике: для скрининга суицидального риска сутки, для
адаптационного профиля неделя.

**Разбор.** Исход ставится на случай целиком, а не на каждый пункт: специалист
принимает одно решение о человеке. Существующие поля исхода переезжают на
`alert_cases`; калибровка ROC и PPV начинают считаться по случаям — это
методологически правильнее, потому что пять пунктов одного человека не пять
независимых наблюдений.

**Миграция.** Существующие тревоги сворачиваются в случаи по правилу «один
человек + одна методика + сутки»; исходы переносятся: если по пунктам они
расходятся, берётся самый тяжёлый и в примечании записывается, что случай
собран автоматически.

**Экран.** Список случаев с приоритетом, поиск по фамилии и подразделению,
фильтры «срочность / подразделение / период / кому назначен», курсорная
пагинация, счётчик «разобрано сегодня». Раскрытие случая показывает пункты.

**Критерий готовности:** на 400 открытых случаях дежурный находит нужного
человека за три действия, а первый экран отдаётся меньше чем за 300 мс.

### 9.2 Списки не отдаются целиком — ✅

Где сортировка идёт по SQL-полю — курсорная пагинация: случаи риска, журнал,
повторные замеры. Курсор — «значение сортировки + идентификатор», а не номер
страницы: список меняется прямо во время разбора.

Важная тонкость всплыла на повторных замерах: там строки группируются по
человеку, и условие курсора обязано стоять на **агрегате**. Фильтр по строкам
отсекал отдельные замеры, но у человека оставались более старые — и он
выпадал на следующей странице снова, уже с меньшим максимумом. Пагинация по
группам фильтрует по тому же значению, по которому сортирует.

Где сортировка идёт по ФИО — пагинации нет и быть не может: имя зашифровано,
упорядочить его в SQL нечем, а открытая копия рядом обменяла бы защиту
персональных данных на удобный запрос. Там поиск на сервере с потолком
выдачи и честной пометкой «показано не всё».

Заодно свёртка «кто проходил повторно» переехала в базу: раньше в память
выбирались все завершённые прохождения ради подсчёта, который база делает
одной группировкой.

Результат: пациенты 68 → 16 КБ, повторные замеры 66 → 9 КБ, случаи риска
318 → 43 КБ.

Единый механизм по образцу `routes/audit.ts`: `?limit&cursor`, ответ
`{ items, nextCursor }`. Применить к тревогам/случаям, пациентам, динамике,
батареям, прохождениям, направлениям.

В консоли — «загрузить ещё» в `DataTable` и бесконечная подгрузка там, где
список читают подряд. Потолок `limit` в схеме запроса, чтобы никто не
запросил всё разом.

**Отдельно:** CSV-выгрузка не должна упираться в пагинацию — она идёт
потоком, а не собирает массив в памяти.

### 9.3 Очередь работы специалиста — ✅

Сейчас входящее рассыпано по трём экранам: тревоги, незакрытые назначения,
открытые направления. Нужен один: «что от меня ждут сегодня», отсортированное
по срочности, с возможностью взять случай на себя (`assignedTo`) — чтобы двое
дежурных не разбирали одного человека дважды.

### 9.4 Ответственный и передача смены — ✅

«Взять на себя» и «отпустить» с пометкой, кто взял. История случая
собирается из журнала доступа выборкой, а не отдельной таблицей: всё уже
пишется туда, и вторая запись о том же означала бы два источника истины о
клиническом решении.

Нужно это при передаче смены: заступивший видит, кто брал случай, кто
отпускал и почему он до сих пор открыт.

`assignedTo` на случае, «взять на себя» / «передать», журнал передач.
На «Сводке» — сколько случаев на мне и сколько без ответственного.

### 10.2 Сбор ошибок — ✅

Self-hosted GlitchTip (совместим с Sentry SDK) в `app.onError`, в консоли и в

### 10.3 Метрики — ✅

доля пятисоток выше процента; открытых случаев больше порога дольше суток.

### 10.4 Структурные логи — ✅

JSON вместо строк, с идентификатором запроса и без тел. Уровень из

### 10.5 Проверка восстановления по расписанию — ✅

Скрипт бэкапа есть, но «бэкап, который ни разу не разворачивали, — не бэкап».

## Этап 11 — Интерфейс: система вместо набора экранов

Цель не «покрасить», а сделать так, чтобы новый экран нельзя было собрать

### 11.1 Токены и типографика — ✅

### 11.2 Библиотека компонентов — ⏳ (витрина есть, экраны ещё не переведены)

## Этап 12 — Мобильное приложение

### 12.1 Ревизия навигации целиком — ✅

Пройдены все четырнадцать экранов. Ловушек оказалось две.

**Аналитика.** Вкладка переадресовывала в отдельный стек заменой: возвращаться
некуда, панель вкладок скрыта, системной стрелки нет. Добавлен выход к
вкладкам на корне раздела.

**Согласие.** На экране была одна кнопка — «соглашаюсь». Не согласный не мог
ни отказаться, ни выйти: только убить приложение и вернуться на тот же экран.
Это хуже, чем ловушка навигации: согласие, от которого нельзя отказаться,
согласием не является. Добавлен отказ — выводит из учётной записи и
объясняет, что делать дальше.

Остальные экраны выход имеют: вкладки — панель вкладок, вложенные экраны
аналитики — системную стрелку, прохождение — стрелку и подтверждение выхода,
регистрация — «назад ко входу», вход — корень неавторизованного потока.

Найденная ловушка с аналитикой исправлена, но проверить нужно все переходы:
каждый экран обязан иметь очевидный выход, а системный жест «назад» —
работать всюду. Отдельно: поведение при переходе по ссылке-приглашению и
возврат из прохождения.

**Проверка:** сквозной сценарий на симуляторе, где каждый экран открывается и
покидается без перезапуска приложения.

### 12.2 Экран прохождения — ✅

Главный экран продукта; на нём человек проводит от 5 до 40 минут.

- возврат к первому неотвеченному при попытке завершить;

### 13.1 Печатный отчёт по человеку — ✅

Сводка консилиума печатается, но отчёт по одному прохождению — только
экранный. Нужен документ учреждения: шапка, паспортная часть, профиль,

### 13.2 Групповой отчёт по подразделению — ✅

«Состояние 1-го батальона за квартал»: охват, распределение по степеням,

### 13.3 Повторные замеры по протоколу — ✅

Просроченные повторы попадают в очередь работы отдельным видом. Признак
простой и честный: доступ выдан протоколом наблюдения, срок вышел, и с

протокол.

Протоколы наблюдения есть; не хватает экрана «кто просрочил повтор» и
эскалации по просрочке.

# Часть III. Ревью кода и тестов

Первые две части закрывали функциональность. Эта — про то, как код написан
и чем он проверен. Ревью сплошное: читались критические пути, а не
подсчитывались метрики.

Размер: 38 тысяч строк кода, 4,2 тысячи строк тестов (11 %). Но важнее
распределение: у API 17 тысяч строк и 2,6 тысячи строк интеграционных
тестов, у консоли 10,6 тысячи строк и **34 строки тестов**, у мобильного
приложения 6,9 тысячи строк и **ни одного**.

---

## Что показало ревью

### Р.1 Гонка запросов: устаревший ответ затирает свежий — критично

На экране аналитики фильтр периода шлёт запрос на каждое нажатие клавиши.
Запросы разной тяжести идут разное время: широкий период — 244 мс, узкий —
89 мс. Если пользователь сузил период, ответ по **широкому** приходит позже
и затирает правильные данные.

Человек видит аналитику за период, который не запрашивал, и узнать об этом
не может: цифры выглядят настоящими. Для клинических данных это худший вид
ошибки — тихая и правдоподобная.

Проверено: 41 место грузит данные в `useEffect` без отмены предыдущего
запроса. То же на выборе версии методики, подразделения, фильтрах случаев.

### Р.2 Фронтенд держится на шести неглубоких смоуках

17,5 тысячи строк интерфейса и один тест на 34 строки. Смоук по тридцати
экранам проверяет, что страница отрисовалась, — этого достаточно, чтобы
поймать падение, и совершенно недостаточно, чтобы поймать неверную логику:
сортировку, фильтрацию, пересчёт, состояния формы.

Чем это плохо конкретно: половина находок части II — ошибки именно в такой
логике (пагинация по агрегату, курсор, подсчёт долей). В интерфейсе такие же
ошибки никто не поймает.

### Р.3 Девятнадцать эндпоинтов отдают голый массив

`c.json(rows)` вместо `c.json({ items, ... })`. Добавить к такому ответу
общее число, курсор или пометку «показано не всё» нельзя, не сломав клиента.
Это уже стоило работы: списки пациентов и повторных замеров пришлось
переделывать вместе с клиентами, когда понадобилась пагинация.

### Р.4 Двадцать два экрана застревают в ошибке

`setError` при отказе, но `setError(null)` перед новым запросом нет. Один
сетевой сбой — и экран показывает ошибку, пока страницу не перезагрузят,
даже если связь давно вернулась.

### Р.5 В консоли нет обработки отсутствия связи

В мобильном приложении есть очередь, полоса состояния и кэш последнего
чтения. В консоли — ничего: при упавшем API каждый экран показывает
техническое сообщение без объяснения и без повтора. Специалист в кабинете
с плохим Wi-Fi видит то же, что при поломке сервера.

### Р.6 Гонка чтение-запись в заключениях

`PUT /conclusions/...` читает последнюю версию, вычисляет следующий номер и
пишет — без транзакции. Двое специалистов одновременно получат конфликт по
уникальному индексу, то есть пятисотку вместо понятного отказа. Данные
целы — спасает индекс, — но пользователь видит «внутреннюю ошибку».

### Р.7 Мелкое

- `DataTable` использует индекс как ключ строки: при сортировке React
  переиспользует DOM не по назначению.
- `startedAt` и другие даты в схемах приходят как `z.string()` без проверки:
  мусор доходит до Postgres и падает пятисоткой вместо четырёхсотки.
- `integration.test.ts` — 2 632 строки одним файлом; найти в нём нужный тест
  и понять покрытие уже трудно.

## Этап 14 — Корректность интерфейса

### 14.1 Отмена устаревших запросов — ✅

Один хук `useResource` на все загрузки: отменяет предыдущий запрос,
игнорирует ответ, пришедший после следующего, сбрасывает ошибку перед новой
попыткой и умеет повтор.

Не «поправить сорок мест по очереди», а убрать возможность написать
неправильно: если данные грузятся только через хук, гонка не воспроизводима.

Сделано: хук написан и покрыт тестами; в нём же живёт опрос по таймеру для
живых экранов (забытый в экране `setInterval` продолжал ходить в сеть со
скрытой вкладки) и `patch` для ответа, который сервер вернул после действия.
Переведены Dashboard, Worklist, Referrals, Audit, Access, Batteries, Invites,
Schedules, Norms, KioskSessions, CaseSummary, Compare, UnitReport, Administer,
ApiDocs, BlankForm, KeyPrint, список методик конструктора, Admin, редактор
заключений, Surveillance, аналитика методики.

Постраничные списки получили свою форму хука — `usePagedResource`. Гонка там
коварнее: пока летит ответ на «показать ещё», человек меняет фильтр, и хвост
старой выборки дописывается к новой. Список выглядит правдоподобно и содержит
чужие строки. Тревоги и пациенты переведены на него, задержка ввода тоже
переехала в хук.

Из оставшихся useEffect ни один не грузит данные: это автосейв конструктора,
горячие клавиши и конечный автомат киоска.

### 14.2 Состояние сети в консоли — ✅

Отказ с `status === 0` — не ошибка экрана, а отсутствие связи, и говорить
об этом надо иначе: полоса «нет связи с сервером» с повтором, как в
мобильном приложении. Экран при этом держит последние данные, а не
обнуляется.

Сделано компонентом `Screen`: он же задаёт один порядок трёх состояний
загрузки на всех экранах. Раньше каждый писал их сам и писал по-разному —
где-то обрыв связи показывался как поломка, где-то экран навсегда оставался
пустым.

### 14.3 Ответы API — всегда объект — ✅

Девятнадцать эндпоинтов перевести на `{ items, total? }`. Разом, а не по
мере надобности: каждая переделка «когда понадобится» — это ещё один заход
в клиенты.

Сразу же нашлось, чего этой формы не хватало: реестр направлений режется
двумястами записями, и двести первое молча исчезало — экран выглядел полным.
Теперь ответ несёт `truncated`, и на экране про обрыв сказано.

2 745 строк одним файлом разделены на семь: права, прохождения, батареи,

# Часть IV — Новое поколение (этапы 17–31)

## Откуда этот план

Система работает и закрывает то, ради чего писалась: методики, подсчёт,

Точка отсчёта на сегодня: 45 тыс. строк TypeScript, 33 экрана консоли,
18 экранов мобильного приложения, 121 маршрут API, 39 таблиц, 32 миграции,
5 методик, 315 тестов и 59 сквозных сценариев.

Чего в системе нет вовсе — и что определяет границы этого плана:

- **Библиотеки компонентов.** Весь интерфейс консоли — 819 строк рукописного
  CSS и собственные графики на SVG. Это дёшево обошлось на старте и стало
  потолком: каждый новый экран собирается вручную, а согласованность держится
  на внимательности.
- **Реального времени.** Ни одного канала: ни SSE, ни веб-сокетов, ни
  `LISTEN/NOTIFY`. Тревога видна, когда экран открыт и опрошен по таймеру.
- **Пуш-уведомлений.** Мобильное приложение молчит. Назначили обследование —
  человек узнает, когда сам зайдёт.
- **Единого хранилища офлайн-состояния.** Очередь сдач лежит файлами, кэш
  контента — отдельно; полноценной локальной базы и движка синхронизации нет.
- **Клинического контура за пределами тестирования.** Есть заключение и
  направление; нет заметок приёма, плана лечения, целей, маршрутов помощи.
- **Адаптивного предъявления.** МЛО-200 предъявляется целиком всегда.
- **Интеграций.** Система замкнута: ни FHIR, ни каталога учреждения, ни
  обмена с МИС.

Всё это — не упрёк прошлым решениям, а перечень того, что стало узким местом
именно потому, что базовое работает.

**Сквозной принцип части IV:** каждое новшество либо снимает работу с
человека, либо показывает то, чего он раньше не видел. Функция, которая
делает ни того ни другого, в план не попадает, сколько бы модно она ни
выглядела.

## Этап 17 — Язык интерфейса: полный редизайн (L, 4–5 недель)

Задача не «освежить», а сменить породу: сейчас консоль выглядит как
внутренняя админка, а должна выглядеть как пульт. Требование заказчика —
после редизайна приложение не должно узнаваться. Значит меняется всё:
палитра, шрифт, сетка, плотность, движение, поведение таблиц и графиков.

Ограничения, которые редизайн не имеет права нарушить: контраст в кабинете с
плохим светом, читаемость на 13-дюймовом ноутбуке, печать на монохромном
принтере, работа с клавиатуры без мыши, украинский и русский в одном
макете (длина строк отличается до 15 %).

### 17.0 Направление: «Пульт» — ✅

Прежде чем трогать код, фиксируется визуальное направление. Без него
редизайн растворится в переборе оттенков.

**Метафора.** Не «медицинская карточка» и не «дашборд стартапа», а пульт
дежурного: тёмная поверхность, на которой светятся только те цифры, которые
сейчас важны. Приложение работает в кабинете с плохим светом, часто ночью, и
человек за ним ищет глазами отклонение, а не читает подряд.

**Тёмная тема — основная.** Светлая делается полноценно (кабинеты с окном,
показы, печать), но проектируется второй. Это разворот: сейчас всё наоборот.

**Палитра.** Ground — глубокий сине-зелёный сланец, не чёрный: чистый чёрный
на матрице даёт ореолы вокруг мелкого текста.

| Роль | Тёмная | Светлая |
|---|---|---|
| Основание | `#0C1416` | `#F7F9F8` |
| Поверхность | `#121D20` | `#FFFFFF` |
| Приподнятая | `#18272B` | `#F0F4F3` |
| Границы | `#22353A` | `#D9E2E0` |
| Текст основной | `#E8F0EE` | `#0E1A1C` |
| Текст вторичный | `#9DB2B0` | `#4A5C5B` |
| Акцент | `#FFB000` (сигнальный янтарь) | `#B26A00` |

Янтарь — единственный акцент, и он занят: это «требует внимания». Всё
остальное — оттенки сланца. Ошибка большинства интерфейсов такого рода в том,
что акцентом красят кнопки «сохранить», и тогда акцент перестаёт что-либо
значить.

**Выраженность** — отдельная шкала, не пересекающаяся с акцентом: от
приглушённого зелёно-серого (норма) через охру к сигнальному красному
(тяжёлая). Прогоняется валидатором на дальтонизм; в печати заменяется
штриховкой.

**Типографика.** `e-Ukraine Head` для заголовков и крупных чисел,
`e-Ukraine` для текста, моноширинная ступень для баллов и кодов. Крупные
числа — не декоративный приём, а суть: на панели дежурного цифра «34
открытых случая» должна читаться с двух метров.

**Фирменные приёмы**, по которым интерфейс будет узнаваться:

1. **Полоса тяжести** слева у каждой карточки случая — единственный цветной
   элемент в спокойном экране.
2. **Сетка-миллиметровка** на графиках: очень слабая, но заметная — отсылка к
   бумажным бланкам, на которых эти методики жили полвека.
3. **Крупные числа с моноширинными цифрами** и подписью под ними, а не рядом.
4. **Разделители-волосинки** вместо карточек с тенями: плотность важнее
   воздуха, когда на экране двадцать строк.
5. **Клавиши на виду**: у каждого действия подпись клавиши, а не «есть в
   справке».

**Что уходит.** Скруглённые карточки с тенями, синие ссылки, серые кнопки,
эмодзи в подписях, центрированные заголовки, «панели» с рамками вокруг
всего. То есть почти всё, что сейчас на экране.

### 17.1 Токены вместо значений — ✅

Сейчас цвета и отступы живут числами прямо в разметке (`style={{ marginTop: 8 }}`
встречается в консоли больше сотни раз). Первым делом — трёхслойная система
токенов, иначе любой редизайн придётся делать дважды.

- **Слой 1, палитра:** сырые ступени (`--teal-100…900`), без смысла.
- **Слой 2, семантика:** `--surface-base/raised/sunken`, `--ink-primary/secondary/muted`,
  `--accent`, `--border-subtle/strong`, `--focus`. Компоненты знают только этот слой.
- **Слой 3, компонентные:** `--card-padding`, `--table-row-height` — производные,
  переопределяются режимом плотности.

Тема выбирается тремя состояниями (светлая, тёмная, системная), как уже
сделано в мобильном приложении. Тёмная — не инверсия светлой, а отдельно
подобранный набор: инверсия убивает иерархию поверхностей и делает тени
бессмысленными.

**Проверка:** ни одного шестнадцатеричного цвета вне палитры — линт-правило в
CI; контраст каждой пары «текст на поверхности» считается скриптом, а не
глазом (у нас уже был случай, когда жёлтый давал 1.83:1).

### 17.2 Типографика — ✅

Сейчас системный шрифт. Предлагается пара с украинской родословной:

- **Дисплей:** `e-Ukraine Head` — государственная гарнитура Украины, открытая
  лицензия, спроектирована с кириллицей как основным алфавитом, а не
  дорисованной. Для заголовков экранов и крупных чисел.
- **Текст:** `e-Ukraine` (или `Onest` как запасной) — те же принципы, ровный
  ритм на длинных подсказках.
- **Цифры:** отдельная моноширинная ступень для таблиц и баллов;
  `font-variant-numeric: tabular-nums` обязателен везде, где цифры стоят
  столбиком.

Шрифты self-hosted в `woff2`, подмножество кириллицы + латиница, `font-display: swap`.
Внешних CDN нет и не будет: CSP закрыт намеренно.

Масштаб — модульный (1.2), шесть ступеней, ни одного размера вне шкалы.
Строка основного текста ограничена 68 знаками: сейчас подсказки растягиваются
на всю ширину и читаются плохо.

**Проверка:** макет держится, когда украинский текст на 15 % длиннее русского —
отдельный сценарий в e2e снимает скриншоты обоих языков и сравнивает высоты.

### 17.3 Оболочка и плотность — 🟡 (рельса, плотность, верхняя панель — есть; три панели пока только на разборе)

Сегодня боковое меню фиксировано, а весь экран — одна колонка карточек.
Становится:

- **Рельса вместо меню.** 56 px с иконками и подсказками; разворачивается по
  наведению и по `⌘\`. На 13" это возвращает 200 px рабочей ширины.
- **Три панели.** Список → детали → контекст. Разбор случаев, пациенты,
  направления и журнал переходят на эту схему: перестаёшь терять место в
  списке при каждом открытии карточки.
- **Плотность.** Два режима: «просторный» (обучение, показ) и «плотный»
  (ежедневная работа: на экране 24 строки таблицы вместо 14). Хранится в
  профиле, переключается в палитре команд.
- **Шапка страницы** превращается в панель действий с хлебными крошками,
  первичным действием и переполнением; сейчас действия разбросаны.

**Проверка:** сценарий «разобрать десять случаев» проходится клавиатурой без
единого клика и без прокрутки на ноутбуке 1440×900.

### 17.4 Движение — 🟡 (пружины, скелеты, reduced-motion — есть; View Transitions — нет)

Анимация не для красоты: она отвечает на вопрос «откуда это взялось».

- Переходы между экранами — через `View Transitions API` (в Chrome и Safari
  уже есть, деградирует в мгновенную смену).
- Общий элемент: строка списка «раскрывается» в карточку — видно, что
  открылось именно то, на что нажали.
- Пружины, а не кривые Безье, для всего, что двигается по инициативе
  человека; длительности 120/200/320 мс, дольше — только для больших панелей.
- Скелеты вместо спиннеров (уже частично есть), с волной по направлению
  чтения.
- `prefers-reduced-motion` выключает всё, кроме смены непрозрачности.

**Проверка:** тест проверяет, что при `prefers-reduced-motion: reduce` ни один
элемент не имеет `transform`-анимации.

`Pagination`, `Progress`, `Meter`, `Spinner`, `Skeleton`, `Empty`,
`ErrorState`, `Kbd`, `Card`, `Stat`, `Divider`, `ScrollArea`, `Resizable`,
`SplitPane`, `Tree`, `Timeline`, `Stepper`, `CommandPalette`, `DataGrid`.

Поведенческая основа — headless-примитивы (Radix или Base UI): фокус-ловушки,
`aria`, порталы, ролевые модели. Писать это руками ещё раз — недели работы и
гарантированные дыры в доступности; здесь как раз тот случай, когда
зависимость дешевле своего кода.

Стили — CSS-модули на токенах либо vanilla-extract (типобезопасные токены,
ноль рантайма). Tailwind сознательно не берём: в проекте много длинного
украинского и русского текста в разметке, и утилитарные классы делают её
нечитаемой.

**Проверка:** витрина (`/uikit`, уже существует) становится настоящей: каждое
состояние каждого компонента на странице, скриншотные тесты по ней.

### 17.6 Таблицы — 🟡 (виртуализация, сохранённые виды, настройка колонок и фасеты есть; группировка, множественный выбор и разворачиваемая строка впереди)

`DataTable` умеет сортировку, CSV и ключи строк. Становится `DataGrid`:

- виртуализация (списки на 9 000 пациентов сейчас рендерятся целиком);
- закреплённые колонки и шапка;
- настройка колонок: видимость, порядок, ширина — с сохранением в профиле;
- группировка и агрегаты в подвале;
- множественный выбор с действиями над выборкой (назначить, выгрузить);
- фасетные фильтры над таблицей с подсчётом «сколько будет» до применения;
- **сохранённые виды**: «мои просроченные», «рота 3, тяжёлые» — со ссылкой,
  которую можно передать;
- разворачиваемая строка вместо перехода на отдельный экран;
- выгрузка видимого среза, а не всего (сейчас CSV берёт текущий вид — это
  сохраняем, но добавляем выбор).

**Проверка:** 10 000 строк прокручиваются без падения кадров; сохранённый вид
переживает перезагрузку и открывается по ссылке у другого сотрудника с теми
же правами.

### 17.7 Графики — 🟡 (перекрестье, подсказка, имя для диктора — есть; visx, брашинг, малые кратные впереди)

Свои SVG-компоненты честно работают, но не масштабируются. Переход на
`visx`/`d3-scale` (сетка, оси, шкалы, брашинг — чужие; отрисовка и палитра —
свои, чтобы не потерять правила из `dataviz`).

Новое:

- **Перекрестье и подсказка** на всех временных рядах;
- **выделение диапазона** (brush) с синхронизацией нескольких графиков;
- **малые кратные** для сравнения подразделений — сейчас всё в одном графике;
- **спарклайны** в строках таблиц (динамика шкалы прямо в списке пациентов);
- **доверительные полосы**: T-балл без интервала ошибки вводит в заблуждение,
  а SEM у нас уже считается;
- **аннотации на оси времени**: ротация, госпитализация, начало терапии —
  чтобы изменение читалось вместе с событием;
- **тепловая карта пунктов** (человек × вопрос) для поиска небрежного
  заполнения — сейчас это таблица чисел.

**Проверка:** палитра прогоняется валидатором на CVD и контраст; ни один
график не остаётся без табличного представления (доступность).

### 17.8 Печать как отдельная поверхность — 🟡 (стили печати и штриховка вместо цвета — есть; пакетная печать впереди)

Отчёты подшивают в дело, и печать — не побочный режим, а второй интерфейс.

- Своя таблица стилей: сетка A4, поля под подшивку, колонтитулы с номером
  страницы, датой и тем, кто распечатал.
- Разрывы страниц управляемые: шкала не разрывается посередине.
- Монохромный режим: выраженность кодируется штриховкой, а не цветом, —
  на чёрно-белом принтере красное и жёлтое неразличимы.
- QR-код на бланке ведёт на цифровую версию прохождения.
- Пакетная печать: все заключения подразделения за период одним документом с
  оглавлением.

**Проверка:** сравнение PDF-снимков в CI (headless-печать), чтобы вёрстка не
разъезжалась незаметно.

### 17.9 Доступность — 🟡 (контраст, фокус, forced-colors, имена графиков — есть; полный аудит 2.2 впереди)

Цель — WCAG 2.2 AA, проверяемая, а не декларируемая.

- Видимый фокус с толщиной 2 px и смещением, никогда не `outline: none`.
- Порядок табуляции соответствует визуальному; ловушки фокуса в диалогах.
- Живые области (`aria-live`) для тревог и результатов сохранения.
- Подписи ко всем полям (в конструкторе их нет — там `label` не связаны).
- Целевые размеры ≥ 24×24 CSS-px (2.2 добавила это требование).
- Поддержка `forced-colors` (высококонтрастный режим Windows) — в военном
  учреждении встречается чаще, чем кажется.

**Проверка:** axe-прогон уже в CI; добавляется прогон в тёмной теме и в
`forced-colors`, плюс ручной чек-лист клавиатурного прохода.

### 17.10 Экран за экраном — ⬜ (L)

Редизайн не «перекраска»: у каждого экрана меняется устройство.

Сделано на сегодня: сводка, разбор случаев, хронология (новый экран),
витрина. Остальное — впереди.

## Этап 18 — Оболочка: как приложением пользуются (M, 2 недели)

Редизайн отвечает на «как выглядит», этот этап — на «как этим работают».

### 18.1 Палитра команд — ✅

`⌘K` открывает единое окно: переход к любому экрану, поиск пациента, методики,
батареи, действие («назначить», «выписать направление», «переключить

### 18.2 Сохранённые виды и общие ссылки — ✅

Фильтры уже живут в адресе. Добавляется: назвать текущий срез, закрепить его
в боковой рельсе, поделиться ссылкой с коллегой (права проверяются у
получателя, а не наследуются). Таблица `saved_views` (владелец, область,
параметры, общий/личный).

### 18.3 Центр событий — 🟡 (лента событий сессии есть; постоянный журнал и группировка впереди)

Одно место, где видно всё, что произошло, пока тебя не было: новые тревоги,
подтверждения, просроченные направления, отработавшие расписания, чужие
изменения в твоих случаях. С группировкой, отметкой «прочитано» и переходом к
источнику. Питается тем же потоком, что и реальное время (этап 19).

### 18.4 Обучение внутри интерфейса — ⬜ (S)

Не тур по экранам, а точечно: подсказка появляется там, где человек впервые
столкнулся с неочевидным (что такое стены, почему шкала лжи закрыла профиль,
чем «подтверждён» отличается от «требует наблюдения»). Показывается один раз,
отключается в профиле. Тексты — в словаре, оба языка.

### 18.5 Персонализация рабочего места — ⬜ (S)

Стартовый экран (сводка / очередь / разбор), плотность, тема, язык, набор
колонок, закреплённые виды — в профиле, синхронно между устройствами. Мелочь,
которая отличает инструмент от сайта.

## Этап 19 — Реальное время (M, 2 недели)

Сегодня тревога о суицидальном риске ждёт, пока кто-нибудь обновит страницу
или сработает таймер на 60 секунд. Для этого класса событий это неприемлемо.

### 19.1 Канал событий — ✅

`GET /api/events` — Server-Sent Events, а не веб-сокеты: поток
односторонний, переподключение встроено в браузер, проходит через любой
прокси. Веб-сокеты понадобятся только для совместного редактирования (18.x),
и тогда добавятся отдельно.

Источник — `LISTEN/NOTIFY` PostgreSQL: обработчик, создавший тревогу, шлёт
`pg_notify`, инстанс API рассылает подписчикам с учётом прав. Права
проверяются на каждое событие, а не при подписке: скоуп админа может
измениться посреди сессии.

### 19.2 Что течёт по каналу — ✅

- новая тревога и эскалация;
- изменение случая (кто взял, кто разобрал) — чтобы двое не разбирали одного;
- прогресс киоск-сеанса (сейчас опрос раз в 10 секунд);
- завершение прохождения — карта пациента обновляется на глазах;
- отработка расписания;
- системные: развёртывание новой версии («обновите вкладку»).

### 19.3 Присутствие и мягкие блокировки — ✅

Видно, кто ещё смотрит на этот случай и кто печатает заключение. Не
запрещаем — предупреждаем: жёсткая блокировка в клинике опаснее, чем
конфликт, потому что человек, взявший случай, может уйти со смены.

### 19.4 Деградация — ✅

Нет канала — молча возвращаемся к опросу по таймеру, полоса «обновления могут
запаздывать». Приложение не должно ломаться от закрытого SSE на корпоративном
прокси.

**Проверка:** e2e с двумя вкладками: в одной берут случай — во второй он
помечается взятым без перезагрузки.

## Этап 20 — Мобильное приложение нового поколения (L, 4 недели)

### 20.1 Черновик на устройстве и досылка — ✅ (частично; SQLite отложен)

Главное сделано: черновик прохождения пишется на устройство, а не только на
сервер. До этого офлайн автосохранение молча ничего не делало — телефон,
севший на сто восьмидесятом пункте МЛО-200 в подвале без связи, стоил человеку
всего прохождения.

- запись в хранилище атомарна (временный файл + переименование): выключение
  посреди записи не оставляет обрезанный JSON вместо двухсот ответов;
- при возобновлении берётся тот черновик, что новее, — правило вынесено в
  чистую `pickDraft` и покрыто тестами, а не спрятано в экране;
- непосланные черновики досылаются тем же проходом, что и очередь сдач: второй
  механизм синхронизации со своими ошибками заводить не за чем;
- в шапке прохождения видно разницу между «сохранено на телефоне» и
  «сохранено на сервере» — она важна человеку.

**Переход на `expo-sqlite` отложен намеренно.** Он ничего не даёт тому, кто
пользуется приложением: одно прохождение одного человека за раз, файлы уже
переживают перезапуск, а атомарность добавлена точечно. Это была бы неделя
переписывания рабочего слоя ради архитектурной опрятности. Вернуться к этому
стоит, если появится сценарий с одновременными наборами данных на устройстве —
например, офлайн-киоск на планшете.

### 20.2 Пуш-уведомления — ✅ (токены, идемпотентная отправка, назначения и тревоги; настройки по типам — впереди)

Таблица `push_tokens`, Expo Push API, настройки по типам событий. Пациенту:
назначено обследование, приближается срок, напоминание о незакрытой батарее.
Специалисту: тревога в его группе, эскалация, просроченное направление.

Без персональных данных в теле: «тревога по методике X в группе Y» — экран
блокировки видят посторонние. Все отправки — в журнал; тихие часы; сводка
вместо шквала, если событий больше пяти.

### 20.3 Прохождение: другая механика — ⬜ (L)

Сейчас список вопросов с прокруткой. Становится:

- карточная подача с жестами и крупными зонами нажатия;
- кольцо прогресса и честная оценка «осталось ~7 минут» по медиане;
- автосохранение на каждом ответе (уже есть) с видимым подтверждением;
- возврат к пропущенным одним движением, а не прокруткой;
- тактильный отклик на выбор (есть `expo-haptics`, используется мало);
- «крупный шрифт» как режим, а не как системная настройка: у части
  обследуемых нет привычки менять настройки телефона;
- ночной режим для обследований в казарме после отбоя;
- пауза с сохранением: прохождение прерывают, и это нормально.

### 20.4 Режим обхода для специалиста — ⬜ (M)

Отдельная навигация в мобильном приложении: список на сегодня, быстрый ввод
за пациента, просмотр карты и заключений офлайн, надиктовка заметки голосом с
расшифровкой на устройстве. Планшет в палате вместо ноутбука.

### 20.5 Киоск и планшет — ⬜ (M)

Сопряжение по QR/NFC вместо ввода токена руками, экран передачи «следующий»,
таймаут бездействия, блокировка выхода (guided access / screen pinning с
инструкцией в RUNBOOK), живой прогресс потока у оператора.

### 20.6 Виджеты, ярлыки, ссылки — ⬜ (S)

Виджет «задания на сегодня» на домашнем экране; быстрые действия по
долгому нажатию на иконку; универсальные ссылки: приглашение открывается
сразу в приложении, а не в браузере.

### 20.7 Skia для графики — ⬜ (M)

Графики мобильного приложения на `react-native-svg` заметно тормозят на
длинных динамиках. `@shopify/react-native-skia` даёт 60 кадров и жесты
(масштабирование, перекрестье) без борьбы.

### 20.8 Обновления и надёжность — ⬜ (S)

EAS Update для доставки правок без магазина, отчёты об ошибках с тем же
фильтром персональных данных, что на сервере, удалённое стирание локальных
данных при потере устройства (по команде с сервера при следующем выходе в
сеть).

## Этап 21 — Клинический контур (L, 5–6 недель)

Самая ценная часть плана. Сейчас система измеряет; после этого этапа она
ведёт случай от скрининга до исхода.

### 21.1 Маршруты помощи — ✅ (шаблоны, ведение, исход, связь с очередью; редактор шаблонов — впереди)

Формализованный путь: скрининг → углублённое обследование → решение →
вмешательство → повторный замер → исход. Сейчас всё это существует по
отдельности и связывается в голове специалиста.

Таблицы `pathways` (шаблон маршрута), `pathway_instances` (человек на
маршруте), `pathway_steps` (шаг, срок, ответственный, состояние). Переходы
автоматические по правилам (попадание в полосу — уже умеем каскадами) и
ручные с обоснованием.

Что это даёт: видно, кто застрял и на каком шаге. Сегодня «отправили к
психиатру и забыли» обнаруживается случайно.

### 21.2 Заметки приёма — ✅ (версии, подпись, шифрование, привязка к маршруту; шаблоны — впереди)

Структурированные записи: жалобы, наблюдение, оценка, план (SOAP или своя
схема учреждения). Шаблоны, автоподстановка результатов последних методик,
версионирование, подпись. Шифруются как заключения; в печать попадает только
подписанное.

### 21.3 План лечения и цели — ✅ (измеримые цели со шкалой, сроком и достоверностью изменения)

Ядро measurement-based care: цель формулируется измеримо («ПТСР по PCL-5 ниже
33 к третьему месяцу»), к ней привязывается шкала и график замеров.
Достоверность изменения уже считается (RCI); теперь она встраивается в
контур: система сама показывает, движется ли человек к цели, и предупреждает,
когда два замера подряд без улучшения.

### 21.4 Консилиум — ✅ (мнения, особое мнение, решение; пометки на шкалах — впереди)

Режим совместного разбора: несколько специалистов открывают карту, оставляют
пометки на конкретных шкалах и пунктах, фиксируют решение и особые мнения.
Протокол — в журнал и в печать. Сейчас сводка для консилиума есть, а самого
процесса нет.

### 21.5 Поддержка решений — ✅

Правила вида «если шкала суицидального риска выше порога и в анамнезе есть
попытка — предложить C-SSRS и уведомить дежурного». Редактор правил для
суперадмина, версионирование, обязательное объяснение («сработало правило
№12, потому что…»).

Категорически без автоматических клинических решений: система предлагает,
человек решает и это фиксируется. Иначе ответственность растворяется.

### 21.6 Риск-путь — 🟡 (план безопасности и дежурная смена — есть; структурированная оценка риска — впереди)

Отдельный, самый строгий контур:

- **Скрининг → структурированная оценка:** при флаге риска предъявляется
  C-SSRS (или её локальный аналог) — не как обычная методика, а как
  обязательный шаг с фиксацией времени.
- **План безопасности** по Стэнли–Брауну: конструктор с пунктами (признаки,
  внутренние стратегии, люди и места, к кому обратиться, телефоны, ограничение
  доступа к средствам). Печатается и остаётся на телефоне пациента офлайн.
- **Ограничение доступа к средствам** — чек-лист беседы, фиксируется факт.
- **Эскалация с таймерами** и подтверждением получения (уже частично есть).
- **Дежурная смена** — ✅: кто сейчас принимает тревоги, видно на сводке;
  правило может адресовать предложение дежурному.

Про C-SSRS отдельно: пункты шкалы защищены авторским правом Колумбийского
университета, и вписать их в репозиторий нельзя. Движок для неё готов —
структурированная оценка это обычная методика с обязательным шагом маршрута;
недостающее здесь не код, а очистка прав, и это записано в `docs/INSTRUMENTS.md`.

### 21.7 Хронология пациента — ✅

Одна ось времени: прохождения, баллы, тревоги, направления, заметки, приёмы,
события маршрута. С масштабированием и фильтром по типу. Сейчас, чтобы
восстановить историю, нужно обойти четыре экрана.

### 21.8 Мульти-информант — ⬜ (M)

Оценка не только самоотчётом: короткие формы для командира, сослуживца,
члена семьи, врача. Ссылка с ограниченным доступом, ответы отдельно,
сравнение перспектив на одном профиле. В военной психодиагностике расхождение
между самоотчётом и наблюдением командира — самостоятельный сигнал.

### 21.9 Кризисный режим учреждения — ⬜ (S)

Массовое поступление: упрощённый поток, только скрининговые шкалы, очередь
сортировки, отключение необязательных шагов, приоритет по тяжести. Включается
одним переключателем и попадает в журнал.

## Этап 22 — Инструментарий методик (L, 4 недели)

### 22.1 Каталог и правовой статус — 🟡 (статус, источник, отметка о сверке и скрытие демо — есть; пакеты и установка в клик — впереди)

Пакеты методик с манифестом: источник, страницы пособия, статус выверки,
права, версия, контрольная сумма. Установка в один клик, обновление с
показом различий. Методики без очищенных прав помечены и не выдаются в
клинические списки — сейчас это записано в README, а должно быть свойством
данных.

Планируемый состав (при условии решения по правам): PCL-5, PHQ-9, GAD-7,
AUDIT, ISI, шкала Бека, C-SSRS, опросник качества сна, ПТСР-скрининг для
военнослужащих, шкалы выгорания для персонала.

### 22.2 Адаптивное предъявление (CAT) — ⬜ (L)

МЛО-200 — двести пунктов; при калиброванных параметрах IRT то же измерение
даёт 60–80 пунктов без потери точности. Это не экономия времени ради
удобства: на длинных методиках качество ответов падает к концу, и последние
пункты измеряют усталость, а не черту.

Порядок работ: офлайн-калибровка 2PL/GRM по накопленным данным (у нас уже
13 тыс. прохождений и SPSS-выгрузка) → хранение параметров пункта → движок
выбора следующего пункта по максимуму информации → правила остановки (SEM,
максимум пунктов, обязательные пункты риска предъявляются всегда) →
эквивалентирование с полной формой, чтобы старые и новые баллы сравнивались.

Обязательное условие: пункты риска и шкалы достоверности не подчиняются
адаптивному отбору. Пропустить вопрос о суицидальных мыслях ради экономии
пяти пунктов недопустимо.

### 22.3 Эквивалентирование версий — ⬜ (M)

Сейчас версия методики иммутабельна, и прохождения разных версий формально
несравнимы. Нужен механизм связывания шкал между версиями (общие пункты,
линейное или equipercentile-приведение) с явной пометкой «баллы приведены».

### 22.4 Конструктор нового поколения — ⬜ (L)

- живой предпросмотр в рамке телефона рядом с редактором;
- перетаскивание пунктов и разделов;
- шаблоны шкал (сумма прямых и обратных, доля, T-баллы) в один клик;
- проверка ключа на игрушечных данных прямо в редакторе: подставить ответы —
  увидеть балл;
- совместное редактирование с присутствием (этап 19);
- ветвление и логика показа в виде схемы, а не списка условий;
- «что изменится» перед публикацией: сколько прохождений останется на старой
  версии, какие шкалы затронуты.

### 22.5 Ввод с бумаги — ⬜ (L)

В части подразделений тестирование останется бумажным. Бланк уже печатается с
QR; добавляется распознавание: фотография бланка → выравнивание по меткам →
чтение отметок → предпросмотр с подсветкой сомнительных → сохранение как
обычного прохождения с пометкой «с бумаги» (длительность не измеряется, и
флаги скорости к нему не применяются — это уже учтено форматированием).

### 22.6 Голосовое предъявление — ⬜ (M)

Для обследуемых с плохим зрением или низкой грамотностью: зачитывание пункта
и вариантов, ответ голосом или крупными кнопками. Распознавание на устройстве,
без отправки звука на сервер.

## Этап 23 — Данные и наука (L, 3–4 недели)

### 23.1 Витрина и предвычисления — ⬜ (M)

Аналитика уже частично считается в SQL, но каждый открытый экран — это
пересчёт по сырым таблицам. Материализованные представления с инкрементным
обновлением (по расписанию и по событию сдачи): распределения, доходимость,
средние по шкалам, динамика по неделям. Экран открывается мгновенно, а не за
секунду.

Партиционирование `answer_events` и `audit_log` по месяцам — они растут
быстрее всех и никогда не удаляются.

### 23.2 Конструктор когорт — ⬜ (L)

Визуальный запрос без SQL: «мужчины 20–30 из рот 1–3, прошедшие МЛО за
последний квартал, с ЛАП ниже 4, у которых есть повторный замер». Результат —
список, сравнение, выгрузка, сохранённая когорта для наблюдения во времени.
Подавление малых ячеек применяется к когорте так же, как к отчётам.

### 23.3 Прогнозные модели — ⬜ (L)

Не «искусственный интеллект», а конкретные задачи с проверяемым качеством:

- вероятность неявки на повторный замер (кому напомнить лишний раз);
- вероятность ухудшения между замерами (кого позвать раньше срока);
- подтверждаемость тревоги по признакам прохождения (порядок разбора).

Условия: логистическая регрессия или градиентный бустинг с объяснимостью,
обучение офлайн, карточка модели (данные, метрики, ограничения, дата),
калибровка (у нас уже есть ROC-панель и PPV), мониторинг дрейфа, возможность
выключить модель одним флагом. Ни одна модель не принимает клинического
решения и не скрывает данные от специалиста.

### 23.4 Поиск по записям — ⬜ (M)

Полнотекстовый поиск по заметкам и заключениям (`tsvector`, украинская и
русская морфология). Семантический поиск (`pgvector`) — только если удастся
считать эмбеддинги локально: отправлять клинический текст во внешний сервис
нельзя, и это не обсуждается.

### 23.5 Воспроизводимость — ⬜ (M)

Выгрузка уже несёт codebook и хэш датасета. Добавляется: снимок параметров
(какие версии методик, какие нормы, какой профиль деидентификации),
готовый скрипт загрузки для R и Python, и запись факта выгрузки в журнал с
указанием цели исследования.

## Этап 30 — Что осознанно не делаем

Список нужен не меньше остальных: он бережёт от «а давайте ещё».

- **Автоматическая постановка диагноза.** Система измеряет и предлагает,
  решает человек. Иначе ответственность растворяется, а ошибка становится
  анонимной.
- **Внешние облачные модели для клинического текста.** Заметки и заключения
  не покидают контур ни в каком виде, включая «обезличенный».
- **Геолокация обследуемых.** Соблазн есть, пользы для диагностики нет,
  риск — прямой.
- **Игровые механики** (баллы, серии, значки) в клиническом инструменте:
  они меняют мотивацию отвечать и портят измерение.
- **Публичный доступ к агрегатам** без явного решения заказчика: даже
  подавление малых ячеек не делает данные о подразделениях безобидными.
- **Замена бумаги там, где она обязательна по регламенту.** Печать остаётся
  первоклассной поверхностью, а не запасным вариантом.

## Что должно измениться в цифрах

План считается выполненным, когда:

- время от сдачи методики с признаком риска до появления её у дежурного —
  меньше минуты, а не до обновления страницы;
- разбор одного случая — меньше минуты работы мышью и клавиатурой (сейчас
  три-четыре перехода между экранами);
- МЛО занимает у обследуемого 12–15 минут вместо 35–40;
- ни один экран консоли не открывается дольше полутора секунд на 9 000
  пациентов;
- доля прохождений, начатых и брошенных, падает вдвое (сейчас видно в
  воронке);
- ни одного «отправили и забыли»: каждое направление и каждый маршрут имеют
  срок и ответственного, а просроченное видно на первом экране.
