## Контекст

Quizzy — система психодиагностики для военно-медицинского учреждения: API (Bun + Hono +
Drizzle + PostgreSQL 16), веб-консоль (Vite + React 19), мобильное приложение (Expo SDK 57),
общий пакет с движком подсчёта. ~17k строк TS. Уже реализовано: версионирование методик,
ключевой подсчёт (K-коррекция, T-баллы, стены, шкалы достоверности), группы и скоупинг
админов (`lib/scope.ts`), журнал доступа включая чтения, тревоги риска с эскалацией,
потоковая телеметрия ответов, психометрия (альфа Кронбаха, item-total), сравнение когорт,
корреляции, SPSS-экспорт, батареи со строгим порядком (серверная проверка), расписания
повторов с идемпотентным исполнителем, печатные бланки и ключи, 4 реальные методики.

Решения пользователя при планировании:
- **Развёртывание: облако/VPS** — можно email/push и внешний мониторинг; выше требования к защите.
- **Приоритет после фундамента: масштаб и полировка** (киоск, приглашения, i18n, рефакторинг).
- **Защита данных: разумный максимум** — всё, что возможно без внешних аудиторов.

Сквозной принцип всей карты: каждый новый фоновый процесс — по образцу `lib/scheduler.ts`
(идемпотентный тик + журнал запусков), каждое действие — в `AuditAction` (`lib/audit.ts`),
каждая выборка — через `surveyScopeFilter`/`assertGroupAccess`, каждый расчёт — чистой
функцией в `packages/shared` с золотым тестом.

## Найденные дефекты — ✅ все 8 закрыты

1. **Репозиторий не под git** — ни одного коммита. Потеря диска = потеря всего проекта.
2. **Дыра авторизации:** `apps/api/src/routes/access.ts:129` — `GET /api/access/patients`
   отдаёт ВСЕХ пациентов (имя, email, подразделение) любому групповому админу без
   фильтра `accessibleGroupIds` и без аудита. Патч: фильтровать по доступным группам + журнал.
3. **Неверное действие в журнале:** `users.ts` пишет `"user.create"` при смене роли
   (`PATCH /:id/role`) — завести `"user.role_change"`.
4. **Мёртвое объявление** `"response.draft"` в `AuditAction` — нигде не эмитится; убрать
   или начать логировать.
5. **CORS `*`** при токенах в localStorage — сузить до allowlist из env.
6. **`GET /health` не проверяет БД** — вернёт ok при упавшем Postgres; добавить `select 1`,
   разделить liveness/readiness. Плюс: «планировщик тикал < 2 ч назад» по `schedule_runs`.
7. **Stop-колбэк планировщика выбрасывается** (`index.ts:59`) — сохранить и вызывать при
   SIGTERM.
8. **Нет смены/сброса пароля вообще** — заблокированного пользователя чинят руками в БД.

### 1.7 E2E-смоук (M) — ✅
Playwright против настоящего стенда: собранная консоль (`vite preview`, не
dev-сервер — в проде отдаётся именно сборка) + живой API + отдельная база
`quizzy_e2e`, пересоздаваемая перед прогоном. Порты 3199/4199, чтобы стенд не
дрался с запущенным dev.

Что проверяется:
- **вход** — отказ по неверному паролю, живучесть сессии после перезагрузки,
  скрытая администрация у группового админа;
- **клинический контур целиком** — тревоги → пациент → сводка → выписать
  направление → принять → завершить → пропадает из открытых, находится с
  фильтром. Проверяется и запрет перескока через ступень: кнопки «Завершено»
  на выписанном направлении просто нет;
- **скоуп** — списки пациентов у двух групповых админов не совпадают;
- **конструктор** — массовая вставка пунктов текстом, проверка структуры,
  публикация, методика в списке;
- **доступность** — axe (WCAG 2.1 AA) на четырёх экранах × две темы.

Файлы `*.e2e.ts`, а не `*.spec.ts`: иначе `bun test` в корне подхватывает их
и падает на импорте `@playwright/test`.

Найдено при внедрении: `db:reset` был сломан с момента написания —
`migrate.ts` закрывает общий пул, и посев в том же процессе писал в мёртвое
соединение; шесть нарушений контраста в обеих темах (приглушённый текст,
активный пункт меню, git-sha под полупрозрачностью).

### 2.2 Офлайн-режим мобилки (L) — ✅

клиентскому id. Индикатор «не синхронизировано: N», запрет логаута при непустой очереди.
`computeProfile` в shared — завершение показывается офлайн; при синке серверный пересчёт
сверяется и расхождения логируются (их быть не должно — общий код).

### 2.4 RCI (M) — ✅
Стандарт measurement-based care (Jacobson–Truax): SEM = SD·√(1−r); r — фактическая
альфа (уже считается), SD — из норм шкалы (`scaleNorms`) или по выборке.

### Снятие методики с использования — ✅

`DELETE /api/surveys/:id` уничтожал по внешним ключам все прохождения, баллы,
тревоги и назначения по методике — клиническую историю живых людей,
необратимо и без подтверждения. Теперь метод снимает методику с
использования: `archivedAt` + кто снял.

Снятая методика исчезает из всего, что смотрит **вперёд** — списки, выдача
доступа, батареи, киоск, расписания, новые прохождения и черновики — и
остаётся во всём, что смотрит **назад**: карта пациента, аналитика, журнал.
Дыры в клинических записях недопустимы: методику вывели из оборота, но
человек её проходил, и это остаётся фактом.

Точка проверки одна на все пути выдачи (`assertSurveysInUse`), иначе шесть
отдельных проверок неизбежно разъедутся. Автоматические выдачи — расписание,
каскад, приглашение — снятую методику молча пропускают и выдают остальные:
расписание работает в усечённом виде, а не встаёт целиком.

Физическое удаление — только с сервера: `bun run survey:purge <id>`. Требует,
чтобы методика уже была снята (между решением и необратимым действием должен
быть промежуток), печатает, сколько прохождений и тревог будет уничтожено, и
требует повторить точное название. Запись в журнал делается ДО удаления —
журнал защищён хэш-цепочкой и переживёт саму методику.

Заодно: `"archived"` убран из перечисления `status`. Значение никогда не
выставлялось и нигде не проверялось, но выглядело рабочим — рано или поздно
им бы «сняли» методику, ничего при этом не запретив.

### Каскады удаления — ✅

Ревизия всех внешних ключей после истории с методиками: где ещё удаление
одной строки уносит клинические данные.

- **Группа** удаляла батареи (`batteries.group_id` каскадный), а с ними
  историю назначений, расписания и сеансы киоска. Методики при этом
  получали `group_id = null` и по правилам `scope.ts` превращались в личные
  черновики создателя — остальные админы группы молча теряли доступ.
  Теперь непустая группа не удаляется.
- **Батарея** проверяла только *открытые* назначения. Завершённое
  назначение — это запись о том, что человек реально проходил набор; каскад
  стирал её, и в карте оставалось прохождение без объяснения, откуда оно.
  Теперь удаляется только батарея, которая ни разу не назначалась.
- **Учётная запись** была связана с созданными ею методиками каскадом:
  одна ручная чистка учётки в `psql` уносила методики вместе со всеми
  прохождениями. Шесть авторских связей (`createdBy` у методик, групп,
  батарей, расписаний, приглашений, сеансов) переведены на `RESTRICT`.
  Колонки `userId` остались каскадными — согласия, назначения и токены
  принадлежат самому человеку и уходят вместе с ним.

Полная карта «что уходит следом» — в RUNBOOK: при ручной работе в psql
защиты приложения не работают.

# Расширение плана: этапы 5–8 (медицинская аналитика и клинический контур)

Составлено 2026-08-26 после закрытия этапов 0–2 и половины этапа 4. Ядро
расширения — два принципа, которых не хватает нынешней аналитике, и четыре
этапа, которые на них строятся.

## Сквозные принципы

### П-1. Стратификация по полу и возрасту — везде

Ни одна метрика не существует «в среднем по больнице»: тревожность женщин
25–34 и мужчин 45+ — разные распределения, и усреднение прячет обе группы.
Правило для ВСЕХ новых и существующих срезов аналитики:

- каждая метрика фасетируется по **полу × возрастной полосе**
  (до 25 / 25–34 / 35–44 / 45+ — полосы уже стандартизованы в системе:
  сравнение когорт, SPSS-экспорт);
- возраст всегда «на момент обследования» (ageAt), не текущий;
- **подавление малых ячеек**: страта с n < 5 не показывается и не
  выгружается («< 5» вместо числа) — стандарт медицинской статистики против
  реидентификации; порог конфигурируем (`SMALL_CELL_FLOOR`);
- при сравнении групп с разной половозрастной структурой показатели
  дополнительно **стандартизуются** (см. 5.5) — иначе «рота А тревожнее
  роты Б» может означать лишь «рота А моложе».

### П-2. Замкнутый клинический контур

Скрининг без верификации — генератор непроверенных чисел. Каждая тревога и
каждый повышенный балл должны получать клинический исход (подтверждён /
не подтверждён / направлен), и эти исходы — сырьё для калибровки порогов
(5.7): система учится на решениях своих же психологов.

## Этап 5 — Медицинская аналитика второго порядка

### 5.1 Стратифицированные срезы — ✅

**Зачем.** Сейчас распределения, статистика пунктов и надёжность считаются
по всей выборке; половые различия норм уже признаны системой (T-баллы по
полу), а аналитика этого не отражает.

**Что.** В аналитике методики — переключатель фасета «все / пол / возраст /
пол×возраст»:
- распределения баллов и интерпретационных полос — по стратам;
- статистика пунктов (среднее, доля «да») — по стратам;
- воронка доходимости — по стратам (женщины бросают на пункте 34?);
- везде подавление ячеек n < `SMALL_CELL_FLOOR`.

**Реализация.** Расширить `routes/analytics.ts` параметром `facet`;
считать в SQL (`GROUP BY sex, age_band`), возрастную полосу — вычисляемым
выражением от расшифрованной даты рождения… **важно**: birthDate шифрован,
SQL-группировка по нему невозможна → добавить в `responses` снэпшот
`respondentAgeBand` и `respondentSex` **на момент сдачи** (заполняется в
persistSubmission; заодно это исторически честнее — пол/возраст фиксируются
такими, какими были при обследовании). Бэкфилл по расшифровке в JS.

**Тесты.** Страта n<5 подавлена; сумма страт = целому; полоса от ageAt на
момент сдачи, не текущего.

### 5.2 DIF по полу, возрасту и языку — ✅

**Зачем.** Пункт «я часто плачу» у мужчин и женщин с одинаковым уровнем
депрессии работает по-разному — суммарный балл смещается не из-за состояния,
а из-за формулировки. Для методик, перенесённых из пособий 1980–2010-х, это
не гипотеза, а ожидание.

**Метод.** Mantel–Haenszel: стратификация по суммарному баллу шкалы
(4–5 страт), в каждой — таблица 2×2 (группа × ответ по ключу);
χ²MH + общий отношение шансов αMH; ΔMH = −2.35·ln(αMH);
классификация ETS: |ΔMH| < 1 — A (нет DIF), 1–1.5 — B (умеренный),
> 1.5 при значимости — C (выраженный).

**Guard-ы (главное).** MH при выборках < 200 на группу ненадёжен
(Fidalgo 2004): при n < 200 — помечать «предварительно», использовать
α = 0.2 вместо 0.05; при n < 50 в любой группе — не считать вовсе.
DIF ≠ приговор пункту: класс C — сигнал на клинический разбор, не
автоматическое исключение из ключа.

**Реализация.** `packages/shared/src/dif.ts` — чистая функция
`mantelHaenszel(strata: {a,b,c,d}[]): {chi2, alphaMH, deltaMH, class}` с
золотым тестом на числовом примере, посчитанном руками. В API — расчёт по
полу и по возрастным полосам (референс — модальная группа) на вкладке
«Пункты» аналитики; в UI — колонка DIF с классами и подсказкой «что это
значит». Отдельно: **DIF по языку предъявления** (см. 7.4) — для двуязычной
системы это уникально важный разрез.

### 5.3 Перцентильные карты по возрасту — ✅

**Зачем.** Норма «одна на всех взрослых» из пособия скрывает возрастной
градиент. Формат врачам знаком по картам роста детей: кривые P10/P25/P50/
P75/P90 по возрасту, точка пациента — на фоне кривых его пола.

**Метод.** Скользящее возрастное окно ±5 лет (минимум 30 наблюдений в окне,
иначе окно расширяется до достижения минимума; честная пометка ширины окна);
квантили по скорректированному сырому баллу. Никакой экстраполяции за
пределы наблюдаемых возрастов.

**Реализация.** Эндпоинт percentile-map в norms-модуле; кривые — линии в
существующем LineChart; страница «Локальные нормы» получает вторую вкладку
«Возрастные кривые». Точка конкретного пациента — в его динамике.

### 5.4 Инвариантность надёжности — ✅

α Кронбаха отдельно по полу и полосам (уже есть машинерия reliabilityOf);
доверительный интервал Фельдта; предупреждение в аналитике при
Δα > 0.10 между группами: «шкала измеряет женщин надёжнее, чем мужчин —
сравнение их баллов менее точно, чем кажется».

### 5.5 Возрастно-половая стандартизация — ✅

**Зачем.** «Рота связи тревожнее штаба» — а рота связи на 10 лет моложе.
Прямая стандартизация: стандарт — половозрастная структура всего учреждения;
для каждого подразделения доля высокого риска пересчитывается «как если бы
структура была стандартной»: `Σ (rate_страта × вес_страта_стандарта)`.

**Реализация.** В сравнении когорт (`routes/comparison.ts`) — вторая колонка
«стандартизовано»; **явный флаг, когда стандартизация меняет порядок
групп** — это самый важный сигнал («сырая разница объяснялась возрастом»).
Чистая функция `directStandardize()` в стат-ядре (8.2) с золотым тестом.

### 5.6 Эпиднадзор: контрольные карты — ✅

**Зачем.** Всплеск доли высокого риска в конкретной роте должен быть виден
на неделе всплеска, а не в квартальном отчёте.

**Метод.** p-карта по неделям (доля прохождений с полосой severe/moderate),
контрольные пределы ±3σ от скользящего базового уровня; для малых
подразделений — EWMA (λ=0.2), устойчивее к малым n. Сигналы: выход за
предел; 8 точек по одну сторону центра (правила Western Electric).

**Реализация.** Страница «Надзор» (или вкладка Сводки): карта на
подразделение × методику; сигнал создаёт запись типа тревоги
(`surveillance_signals`) и письмо админам группы через существующий
рассыльщик. Стандартизованные доли (5.5) — как опция. Стат-ядро:
`pChart()`, `ewma()` с тестами.

### 5.7 ROC-калибровка порогов — ✅

**Зачем.** Пороги пособий получены на чужих популяциях. Когда накопятся
верифицированные исходы (6.1), система может честно ответить: «порог 0.38
у нас даёт чувствительность 0.71 и специфичность 0.83; порог 0.31 —
0.86/0.74».

**Метод.** ROC по (балл, исход подтверждения); AUC; Youden J для
кандидатного порога; PPV/NPV при текущей базовой частоте. **Всё —
стратифицированно по полу** (пороги, как и нормы, могут различаться).
Guard-ы: минимум 30 подтверждённых и 30 отвергнутых исходов на страту;
доверительные интервалы (bootstrap); кандидатный порог публикуется как
интерпретационная полоса новой версии — тем же механизмом, что локальные
нормы, с источником «калибровка по N исходам».

### 5.8 Мониторинг PPV — ✅

Из исходов тревог: доля подтверждённых по методике/месяцу — на Сводке.
Падение PPV — ранний признак дрейфа выборки или усталости персонала от
ложных тревог (alarm fatigue) — то, из-за чего скрининги умирают.

## Этап 6 — Замыкание клинического контура

### 6.1 Исход тревоги — ✅

При подтверждении тревоги специалист выбирает исход: «подтверждена /
не подтверждена / требует наблюдения» + короткий комментарий. Одно поле в
существующем acknowledge — а открывает ROC, PPV и обучение порогов.
Существующие подтверждённые тревоги остаются без исхода (честный null).

### 6.2 Каскадные назначения — ✅

Правило на методике: «полоса ≥ X по шкале Y → автоназначить методику/батарею
Z» (скрининг → углублённая диагностика). Исполняется в persistSubmission
после подсчёта; назначение помечено «каскад от <методика>»; журналируется.
Guard: каскад назначает, но никогда не интерпретирует; циклы каскадов
запрещены валидацией правила.

### 6.3 Протоколы наблюдения — ✅

«Высокий риск → повтор через 7 дней, затем 30» — протокол на полосе
интерпретации. Реализация поверх расписаний: персональное одноразовое
расписание; пропуск повтора — эскалация существующим рассыльщиком.

### 6.4 Направления — ✅

Сущность `referrals`: куда (психиатр / стационар / амбулаторно / командиру /
иное), срочность (планово / срочно / немедленно), статус, основание, ответ
принимающей стороны, ссылки на прохождение и тревогу.

Статусы движутся **только вперёд**: `created → accepted → completed`,
отклонить можно на любом открытом шаге. Принятое направление нельзя
«отменить» задним числом — иначе разрыв контура маскируется правкой записи, а
не фиксируется как факт. Переход через ступень (`created → completed`)
отклоняется с 400.

Реестр открытых направлений — в консоли с бейджем в навигации: незакрытое
направление видно и через месяц. «Отправили к психиатру» без обратной связи —
самый частый разрыв клинического контура, и единственная защита от него —
чтобы запись не пропадала из вида.

### 6.5 Сводка для консилиума — ✅

`GET /api/referrals/summary/:userId` собирает в один ответ: паспортную часть
(пол, возраст, подразделение), по каждой методике — последние баллы шкал с
полосой интерпретации и меткой RCI (достоверный сдвиг / в пределах ошибки),
открытые тревоги, подписанные заключения, направления.

Новизна не в данных — они уже есть на семи экранах, — а в том, что их не надо
собирать за минуту до заседания. Печать даёт документ для подшивки: штамп
«сформирована ⟨дата⟩, ⟨кто⟩» появляется только на бумаге.

Чтение сводки — это чтение всей карты пациента, поэтому пишется в журнал как
`response.read` с пометкой `view: "case_summary"`. Скоуп тот же, что везде:
чужой групповой админ получает 404, а не пустую сводку.

## Этап 7 — Качество данных и психометрический контроль

### 7.1 Person-fit — ✅

Нормированные ошибки Гуттмана: у осмысленно отвечающего человека «тяжёлые»
пункты срабатывают только при высоком общем балле; хаотичный профиль или
«слишком идеальный» (симуляция/аграванация) — флаг качества рядом с
существующими too-fast/straight-line. Чистая функция в стат-ядре; флаг —
в качество прохождения и в отчёт (нейтрально: «паттерн ответов нетипичен»).

### 7.2 Дрейф выборки (PSI) — ✅

Population Stability Index распределения баллов месяц-к-месяцу
(PSI > 0.2 — существенный дрейф): предупреждение «выборка изменилась —
локальные нормы, посчитанные до <дата>, могут не подходить». Стат-ядро +
плашка на странице норм.

### 7.3 Отсев по стратам — ✅

Доходимость и пропуски пунктов по полу×возрасту (фасет 5.1 поверх воронки):
если женщины 45+ систематически бросают методику на середине — их данные
недопредставлены в нормах, и это надо ЗНАТЬ, а не догадываться.

### 7.4 Язык предъявления — ✅ (записывается, DIF по языку считается)

**Записывать язык прохождения** (`responses.lang` — какой язык был у
контента при сдаче; сейчас не фиксируется — слепое пятно двуязычной
системы). Дальше: сравнение α и средних uk vs ru, DIF по языку (5.2) —
«пункт 12 в русском переводе работает иначе, чем в украинском оригинале» —
прямой сигнал на правку перевода.

### 7.5 Тест-ретест ICC — ✅

ICC(2,1) по парам повторных замеров со стабильным интервалом (7–60 дней,
без событий тревоги между) — вторая оценка надёжности, независимая от
альфы. В стат-ядро + строка в аналитике шкалы.

## Этап 8 — Технологическая платформа под аналитику

### 8.1 Витрина фактов — ✅ (обычное view: materialized не наследует RLS)

Материализованное представление `response_facts`: response_id, survey,
version, submitted_week, **sex, age_band (снэпшоты из 5.1)**, unit,
статус качества, плюс баллы шкал wide. Refresh — фоновым тиком (образец —
планировщик). Аналитика 5.x читает витрину, а не гоняет JOIN-ы по живым
таблицам; RLS на витрину — те же политики.

### 8.2 Стат-ядро — ✅ 9 функций, 23 золотых теста

`packages/shared/src/stats2/`: mantelHaenszel, directStandardize, pChart,
ewma, roc/auc, icc, psi, guttmanErrors, quantile — **все чистые, все с
золотыми тестами на примерах, посчитанных руками** (дисциплина RCI
показала себя). Ни одна формула не живёт в маршруте.

### 8.3 Long-format экспорт — ✅ (parquet — при запросе)

Long-format CSV (response_id, scale, value — удобен R/pandas) рядом с wide;
parquet — при реальном запросе. Страты и снэпшоты пол/возраст — из витрины,
с теми же профилями деидентификации и подавлением малых ячеек.

### 8.4 Кэш аналитики — ✅ (инвалидация по отпечатку данных)

Ключ (survey, version, facet, диапазон недель); инвалидация по
submitted_week — свежая неделя пересчитывается, история кэшируется вечно.

## Критерии честности (общие для этапов 5–7)

1. Ни одно число без n; ни одна страта n<5 наружу.
2. Ни один статистический вердикт без guard-а малой выборки и пометки
   «предварительно» в серой зоне.
3. Ни одна формула вне стат-ядра; ни одна функция ядра без золотого теста.
4. Автоматика назначает и сигналит, но не диагностирует: последнее слово —
   у специалиста, и это написано в каждом соответствующем интерфейсе.
