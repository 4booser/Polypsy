# Эксплуатация Quizzy

Практика: развернуть, обслуживать, разбирать инциденты. Архитектура и
инварианты — в README; статус работ — в ROADMAP.md.

## Установка экземпляра

Каждое учреждение получает свою базу — колонок арендатора в таблицах нет. Цена
этого решения эксплуатационная: установка, обновление и резервное копирование
умножаются на число учреждений, и платить её надо явно, а не десятком шагов,
которые кто-то выполнит по памяти и в третьем учреждении забудет один.

```bash
DATABASE_URL=postgres://…/quizzy_hospital1 \
JWT_SECRET=… ENCRYPTION_KEY=v1:… \
PHONE_INDEX_SECRET=… EXPORT_SECRET=… \
INSTITUTION_NAME='Госпиталь №1' \
bun run install:instance
```

Скрипт создаёт базу, применяет миграции, выдаёт роли персонала и заводит
первого суперадминистратора, печатая его пароль **один раз** — нигде не
сохраняя. Записать пароль в файл значило бы оставить в экземпляре учётку с
паролем на диске, а придумать «admin/admin» — оставить её навсегда.

Идемпотентен: повторный запуск на готовом экземпляре ничего не ломает и
говорит, что уже сделано. Установку запускают дважды чаще, чем кажется, —
например когда первая прервалась на середине.

Без `ENCRYPTION_KEY` установка отказывается и предлагает сгенерированный ключ.
Для клинической системы открытые поля — не «режим по умолчанию», а авария. То
же и при запуске сервера: в production процесс без ключа не поднимается.

`PHONE_INDEX_SECRET` и `EXPORT_SECRET` — отдельные секреты, не копии
`JWT_SECRET` (совпадение установка тоже не принимает). Секрет подписи меняют
при подозрении на утечку, а слепой индекс телефона и коды субъекта в
выгрузках обязаны переживать такую смену: иначе дедупликация номеров и
склейка лонгитюда ломаются молча. Обновление работающего экземпляра, где
индексы посчитаны на старом секрете: задать `PHONE_INDEX_SECRET` и прогнать
`bun run --cwd apps/api db:reindex-phones` — номер лежит шифрованным, поэтому
индекс пересчитывается.

После установки: создать боевую роль БД (`scripts/create-app-role.sql`) и
перевести `DATABASE_URL` на неё — RLS действует только для не-владельца
таблиц.

## Обновление нескольких экземпляров

```bash
INSTANCES=/etc/quizzy/instances.txt BACKUP_DIR=/backups ./scripts/upgrade-instances.sh
```

Файл `instances.txt` — по строке на экземпляр: имя и адрес базы.

Порядок для каждого один и тот же и не случаен: снимок базы, миграции,
проверка что приложение поднимается на новой схеме. Снимок первым, потому что
откатывать нечем, если его нет; проверка запуска последней, потому что
«миграции прошли» означает только «SQL выполнился» — несовпадение схемы и кода
вылезет у первого пользователя, а не здесь.

**Останавливается на первом отказе.** Продолжить и обновить остальные значило
бы получить пять учреждений в разных состояниях, из которых неизвестно какое
рабочее. Без `BACKUP_DIR` не запускается вовсе: миграция, которая не
откатывается, без снимка означает потерянные клинические записи.

## Перенос методики между экземплярами

Выгрузка методики (`Методики → выгрузить файлом`) и загрузка в другом
экземпляре. Едут ключи подсчёта, полосы интерпретации и пороги — то, ради чего
перенос и нужен: учреждение, сверившее ключи с пособием, не делает эту работу
заново.

**Не едут три вещи, и каждая по своей причине:**

- **нормы местной выборки.** T-балл значит разное относительно мирной
  популяции и относительно своего госпиталя. Норма, посчитанная по выборке
  одного учреждения и молча уехавшая в другое, означает, что второе считает
  своих людей по чужой популяции и об этом не знает. Нормы из пособия — едут;
- **ссылка на батарею** в полосе интерпретации. Идентификатор принадлежит
  своему экземпляру; в чужом он либо не найдётся, либо укажет на другую
  батарею;
- **отметка о сверке ключей.** Это утверждение учреждения о том, что ключи
  сверены здесь. Перенести её значило бы дать одному учреждению ручаться за
  другое.

Импортированная методика приходит черновиком: публикация — осознанное действие
после сверки, а не следствие импорта.

## Развёртывание (VPS + Docker)

```bash
cp .env.docker.example .env.docker   # заполнить ОБЯЗАТЕЛЬНО (см. чеклист)
docker compose --env-file .env.docker up -d --build
```

Мигрциии применяются контейнером API при старте. Консоль — на 80/443 (Caddy,
TLS автоматом при заданном SITE_ADDRESS), API проксируется через /api.

### Чеклист ввода в эксплуатацию

- [ ] `POSTGRES_PASSWORD`, `JWT_SECRET` (32+ случайных символов) заданы
- [ ] `ENCRYPTION_KEY` задан: `v1:$(head -c 32 /dev/urandom | base64)`
- [ ] `PHONE_INDEX_SECRET` и `EXPORT_SECRET` заданы и не совпадают с `JWT_SECRET`
- [ ] `CORS_ORIGINS` = адрес консоли
- [ ] `SMTP_URL`/`MAIL_FROM`/`CONSOLE_URL` — иначе тревоги только в консоли
- [ ] `OPEN_REGISTRATION=0` — вход пациентов только по приглашениям
- [ ] Создана боевая роль БД (RLS активен только для не-владельца):
      `psql "$DATABASE_URL" -v app_password='…' -f scripts/create-app-role.sql`,
      затем в DATABASE_URL приложения — `quizzy_app`
- [ ] Настроен крон бэкапов (ниже) и проверено восстановление
- [ ] Создан суперадмин, смена его пароля с дефолтного
- [ ] Задан текст информированного согласия (консоль → Учётные записи)

## Записи приёмов

Запись приёма — самые чувствительные данные в системе: не результат методики,
а разговор человека о себе целиком. Отсюда два требования к развёртыванию.

**Аудио лежит файлами, а не в базе.** Каталог задаётся `RECORDINGS_DIR`
(по умолчанию `./data/recordings`), файлы шифруются тем же ключом, что и поля
(`ENCRYPTION_KEY`). Часовой приём — десятки мегабайт; в базе они превратили бы
бэкап в неподъёмный. **Каталог обязан попадать в резервное копирование
отдельно** — скрипт `backup.sh` берёт только базу, и без этого шага
восстановление вернёт карточки без записей.

**Расшифровка — своим whisper.cpp, на этой же машине.**

```bash
# один раз: собрать whisper.cpp и скачать модель
git clone https://github.com/ggerganov/whisper.cpp && cd whisper.cpp && make
bash ./models/download-ggml-model.sh large-v3

# в .env приложения
WHISPER_BIN=/opt/whisper.cpp/main
WHISPER_MODEL=/opt/whisper.cpp/models/ggml-large-v3.bin
```

Облачные сервисы распознавания сюда не подставляются — ни Web Speech API, ни
чужой STT. Отправить запись психотерапевтической сессии наружу значит раскрыть
её третьей стороне, и человек, который говорил о себе, об этом не узнает.

Пока переменные не заданы, расшифровки нет — и это видно на экране приёма
прямым текстом: запись хранится как аудио. Молчание здесь было бы хуже
отсутствия: специалист ждал бы стенограмму, которой не будет.

Расшифровка идёт по одной записи за такт планировщика. Часовой приём на CPU
занимает примерно столько же, сколько длился приём; на машине без GPU
очередь из пяти записей растянется на вечер — это нормально, но об этом надо
знать, планируя нагрузку.

## Бэкапы

```bash
# крон на хосте, ежедневно ночью:
DATABASE_URL=… BACKUP_DIR=/backups BACKUP_PASSPHRASE=… ./scripts/backup.sh
```

Ротация: 7 суточных / 4 недельных / 12 месячных. Дампы всегда шифруются
(age или gpg) — скрипт отказывается работать без парольной фразы.

**Восстановление** — сначала в отдельную базу, проверить, потом переключать:

```bash
DATABASE_URL=postgres://…/quizzy_restore BACKUP_PASSPHRASE=… \
  ./scripts/restore.sh /backups/daily/quizzy_….dump.zst.age
```

Проверку восстановления гонять не реже раза в квартал: бэкап, который ни
разу не восстанавливали, — это лотерейный билет, а не бэкап.

## Ключи шифрования полей

Формат `ENCRYPTION_KEY="v1:<base64>[,v0:<base64>]"` — первый ключ активный,
остальные читают свои старые записи.

**Ротация:** сгенерировать новый, поставить ПЕРВЫМ, старый оставить в списке;
перезапустить API; прогнать `bun run db:encrypt` (перешифрует старое активным
ключом); когда `enc1:v-старый:` в базе не останется — старый ключ убрать.

То же по шагам — в техпанели, раздел «Ключі й секрети» (только суперадмин):
сколько значений и файлов записей приёма лежит на каждой версии ключа, нет
ли данных на ключе, которого нет в окружении (потеря — красным), кнопка
«Перешифрувати» (тот же проход фоном, порциями, с ходом на экране и в
журнале) и последний шаг, который говорит, когда старый ключ пуст.

До волны 10 `db:encrypt` шифровал только открытое и значения на старом
ключе НЕ трогал — обещание строкой выше не выполнялось. Теперь второй проход
переводит на основной ключ всё, что лежит на других, по всем шифрованным
колонкам (`*_enc` и старые имена, см. `lib/keyInventory.ts`) и файлам записей
приёма. Файлы без заголовка читаются основным ключом, то есть ломаются в
момент смены основного: перешифровать их надо сразу после перезапуска.

**Дошифровка идёт сама:** `scripts/upgrade-instances.sh` прогоняет
`db:encrypt` после миграций каждого экземпляра. Прогон идемпотентен —
значения с заголовком `enc1:` он не трогает, — поэтому обновление, которому
дошифровывать нечего, ничего и не меняет. Руками команда нужна только вне
этого скрипта: после включения ключа на уже работающем экземпляре и в
середине ротации. Отдельно это касается **дат рождения**: до исправления
регистрации они уходили в базу открытыми, и на боевых базах их перешифрует
именно этот прогон.

**Утрата ключа** = данные полей не читаемы («не расшифровано» в интерфейсе).
Ключ хранить отдельно от бэкапов БД — иначе это один секрет, а не два.

## Журнал доступа

- Append-only на трёх уровнях: приложение, триггер БД, привилегии боевой роли.
- Целостность: `bun run audit:verify` (или GET /api/audit/verify) — цепочка
  хэшей; при разрыве называется seq первой затронутой записи.
- Сверка идёт и сама — раз в сутки в планировщике; итог последней (и кнопка
  внеочередной) — техпанель → «Цілісність». Разрыв — `log.error` и запись
  `sec.audit_chain_broken` в журнал: на это имя и заводится оповещение.
- Головной хэш из отчёта периодически фиксировать вовне (распечатать,
  отправить) — сверка с внешней копией ловит даже подмену таблицы целиком.

## Разбор инцидентов

- **«Что задеплоено?»** — sha сборки в левом нижнем углу консоли.
- **Тревога не дошла почтой** — журнал: `alert.notified` с channel=none
  означает незаполненный SMTP_URL; escalation отдельной записью.
- **Пациент «не видит методику»** — проверить: опубликована? назначение не
  истекло? батарея со строгим порядком не ждёт предыдущий шаг? роль user
  в системе с RLS видит только published.
- **Пустые выборки у нового маршрута** — забыт requireAuth: без контекста
  RLS отдаёт ноль строк (так задумано).
- **Диск растёт** — консоль → Журнал доступа → Хранилище; answer_events
  сдерживается `ANSWER_EVENTS_RETENTION_DAYS`.

## Киоск

На планшете включить режим одного приложения: iOS — Guided Access
(тройное нажатие боковой кнопки), Android — закрепление экрана. Сеанс
живёт заданное число часов и закрывается оператором; бездействие 4 минуты
возвращает киоск на стартовый экран.

## Учётная запись для показов

`demo@quizzy.dev` — администратор группы, у которого выключены любые изменения.
Ходит по консоли настоящими маршрутами и видит настоящие экраны, но каждый
запрос, меняющий данные, получает 403 и запись в журнал.

Проверка стоит внутри `requireAuth` и смотрит на метод запроса, а не на список
эндпоинтов: перечень безопасных маршрутов устаревал бы с каждой новой
возможностью.

Чтобы сделать такой любую учётку: `update users set read_only = true where
email = '…'`.

## Что нельзя удалять и почему

База связана внешними ключами так, что удаление одной строки может унести
далеко больше, чем видно из интерфейса. Приложение теперь этому мешает, но
при ручной работе в `psql` защиты нет — держите картину в голове.

| Удаляем | Уходит следом |
|---|---|
| методику | прохождения, баллы, тревоги, назначения, все версии |
| группу | батареи → назначения, расписания, сеансы киоска |
| батарею | пункты набора, назначения, расписания, сеансы киоска |
| прохождение | ответы, баллы, тревоги, заключение |
| учётную запись | согласия, назначения, токены — но **не** созданные ею методики |

Что приложение запрещает:

- методику нельзя удалить вовсе — только снять с использования (см. ниже);
- группу — пока в ней есть методики или батареи;
- батарею — если она хоть раз назначалась;
- учётную запись, создавшую методики, группы, батареи, расписания,
  приглашения или сеансы киоска: внешний ключ `RESTRICT` не даст. Сначала
  передайте содержимое, потом закрывайте учётку. Уволенный психолог не должен
  уносить с собой клинический архив отделения.

## Удаление методики

Из консоли методику можно только **снять с использования**: она перестаёт
выдаваться и проходиться, но все собранные прохождения, баллы и тревоги
остаются. Решение обратимо кнопкой «Вернуть в работу».

Физическое удаление — отдельная команда на сервере, и она уничтожает всю
клиническую историю по методике:

```
bun run --cwd apps/api survey:purge <id>                    # показать, что уйдёт
bun run --cwd apps/api survey:purge <id> --confirm "<точное название>"
```

Команда откажется работать, пока методика не снята с использования. Запись о
чистке попадает в журнал доступа **до** удаления и остаётся там навсегда.

Перед чисткой — свежий бэкап. Восстановить иначе будет нечем.

## Проверка контента перед выкаткой

```
bun run --cwd apps/api content:check           # ошибки валят проверку
bun run --cwd apps/api content:check --strict  # предупреждения тоже
```

Встроенные методики проверяются тестом по файлам, но в работе живут ещё
заведённые через конструктор и импортированные — их не проверяет никто, а
поломка ключа не роняет приложение: она молча даёт неверный балл.

Ненулевой код возврата означает «не выкатывать»: ошибка в опубликованной
методике дороже задержки релиза.

## Проверка восстановимости бэкапа

«Бэкап, который ни разу не разворачивали, — не бэкап»: файл может быть
обрезан, зашифрован потерянным ключом или содержать дамп, который не
накатывается. Узнать об этом в день аварии — поздно.

```
DATABASE_URL=postgres://... BACKUP_DIR=/backups BACKUP_PASSPHRASE=... \
  ./scripts/verify-backup.sh
```

Скрипт берёт самый свежий бэкап, разворачивает в одноразовую базу, проверяет
и удаляет её за собой. Что проверяется:

| Проверка | Что ловит |
|---|---|
| возраст файла ≤ 48 ч | расписание бэкапов встало |
| ключевые таблицы непусты | дамп снят не с той базы |
| число миграций совпадает с рабочей | дамп со старой схемы |
| цепочка журнала цела | журнал в бэкапе переписан |

Ненулевой код возврата — повод для оповещения. В cron: раз в неделю, вывод в
систему оповещений.

## Наблюдаемость

**Номер запроса.** Каждый ответ несёт `X-Request-Id`; при ошибке он же
приходит в теле и показывается пользователю в конце сообщения. По нему запись
находится в логе одним поиском — вместо «вчера вечером что-то не
сохранилось». Если перед приложением стоит прокси, проставляющий свой
заголовок, он принимается (просеивается от посторонних символов) и логи
сшиваются.

**Логи.** В production — JSON построчно, в разработке — читаемые строки.
Уровень задаётся `LOG_LEVEL` (debug/info/warn/error). В полях не бывает
персональных данных: маршрут, роль, длительность, код — и ничего из тела.

**Сбор ошибок.** Задайте `SENTRY_DSN` — подойдёт self-hosted GlitchTip.
Без него отправка выключена.

Отправка своя, не через SDK: официальный клиент по умолчанию собирает тела
запросов, заголовки и переменные окружения — ровно то, чего в отчёте из
медицинской системы быть не должно. Уходят пять полей: тип и сообщение
ошибки, стек, маршрут (шаблоном, а не фактическим путём — иначе в него попал
бы идентификатор человека), метод, роль, номер запроса. Перед отправкой
событие ещё раз просматривается на запрещённые поля; при находке отправка
отменяется и пишется в свой лог.

**Метрики.** `GET /metrics` в формате Prometheus. Закрыты общим секретом
`METRICS_TOKEN`; **без него эндпоинт отвечает 404** — выключено значит
выключено, а не открыто для всех.

Что отдаётся: `quizzy_http_requests_total` и `quizzy_http_duration_ms` по
маршрутам (путь берётся шаблоном, а не фактическим адресом — иначе серий
было бы столько же, сколько пациентов), `quizzy_open_alert_cases`,
`quizzy_scheduler_stale_minutes`, `quizzy_database_bytes`,
`quizzy_audit_entries`, `quizzy_uptime_seconds`.

Три оповещения, которые стоит завести первыми:

| Условие | Что случилось |
|---|---|
| `quizzy_scheduler_stale_minutes > 120` или `< 0` | планировщик не тикал два часа или не тикал вовсе |
| `rate(quizzy_http_requests_total{status=~"5.."}[5m]) > 0.01` | доля пятисоток выше процента |
| `quizzy_open_alert_cases` держится выше порога сутки | случаи копятся, их не разбирают |

Счётчики живут в памяти процесса и обнуляются при перезапуске. При нескольких
репликах складывать их надо на стороне сбора: «всего запросов» с одного узла
не равно «всего по системе».

**Техпанель.** `/ops` в консоли — то же для человека: запросы и время ответа
по шаблонам маршрутов, медленные запросы (от 1 с) с номером запроса,
сгруппированные ошибки со стеком, живая лента лога, состояние базы
(размеры, подключения, долгие запросы, блокировки, миграции), такты фоновых
задач и проверки здоровья. Открывается правом `ops.read`: суперадмину оно
есть всегда, разработчику выдаётся личным исключением на экране прав
(группа «Технічна служба»); клинической роли оно не достаётся.

Память панели — кольцевые буферы процесса (последние 5000 строк лога, сутки
поминутных корзин, 200 групп ошибок, 200 медленных запросов): до
перезапуска и одной реплики, и экран так и пишет. Лог в буфере вычищен
поверх правила «без ПДн»: поля с персональными именами скрыты, почта и
телефоны замаскированы. Про секреты панель отвечает только «задан / нет».
Чтение ленты и ошибок пишется в журнал (`ops.logs.read`,
`ops.errors.read`), опросы одного человека склеены по пять минут.

Версию выкатки панель берёт из `QUIZZY_VERSION` (и `QUIZZY_BUILD`, если CI
его задаёт) — docker-compose передаёт их в контейнер api. Без
`pg_read_all_stats` у роли приложения чужие сессии в разделе «База» скрыты,
без доступа к схеме `drizzle` — журнал миграций; раздел говорит об этом
вместо отказа. Выдать, если нужно видеть всё:
`GRANT pg_read_all_stats TO quizzy_app;`
## Режим обслуживания и страница статуса

Техпанель → «Обслуговування». Включает и выключает право «Керувати роботою
системи» (ops.manage), смотреть можно с ops.read.

**Режим обслуживания** — одна кнопка, с текстом для людей и ожидаемым
временем окончания. Пока он включён:

- все изменяющие запросы к API (не GET/HEAD/OPTIONS) получают **503** с
  `Retry-After` (до объявленного конца; без срока — 300 с) и понятным текстом
  на языке человека;
- **кроме** техпанели (`/api/ops/*` — иначе режим не выключить) и входа
  (`login`, `logout`, `refresh`, обмен кода Google);
- чтение работает как обычно;
- баннер видят все: консоль (под верхней полосой), кабинет пациента,
  прохождение методики, экран входа;
- сдачи ответов не теряются: мобилка и веб-кабинет считают 503 (и 502/504)
  временным отказом, кладут сдачу в очередь на устройстве и досылают после
  работ с тем же `clientRequestId`.

Состояние лежит в базе (`service_announcements`, последняя строка), поэтому
переживает перезапуск и одинаково для всех процессов API (кэш — 3 секунды).
Включение и выключение — в журнале доступа (`ops.maintenance_on`,
`ops.maintenance_off`).

Отказы режима — 503, поэтому лог пишет их как `error`, а метрика считает в
пятисотки: оповещение «доля пятисоток» на время работ сработает, и это
ожидаемо.

**Страница статуса** — `/status`, открыта без входа (ссылка с экрана входа):
«працює / обслуговування / збої», текст объявления, время, история
последних объявлений. Без авторов и без технических подробностей.
«Збої» ставят руками из техпанели; автоматически — только если сервер сам
не получил ответа от базы за две секунды. Запись «збої» не закрывают.

## Флаги функций

Техпанель → «Прапорці». Новый экран или поведение включается отдельным
людям и группам без выкатки: всем, классам учётных записей (пациенты —
только целиком), посадам лестницы, людям поимённо (сотрудники), группам
методик, відділенням. Ключи — в `packages/shared/src/featureFlags.ts`,
код спрашивает `useFlag(key)` с типизированным ключом. Флаг — не право:
закрытое правом остаётся закрытым на сервере. Изменения — в журнале флага
и в журнале доступа (`ops.flag_set`).

**Оповещения техпанели** (раздел «Сповіщення»): всплеск 5xx, молчащий
планировщик, рост p95, место на томе записей, провал проверки цепочки
журнала — в Telegram и/или на почту. Каналы — только из окружения:
`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (бот должен состоять в чате),
почта — тем же `SMTP_URL`, что тревоги, адресатам из `OPS_ALERT_EMAIL`
(через запятую; пусто — суперадминам). Панель показывает только «задано /
нет» и кнопку «Відправити тестове». Правила (порог, окно, повтор, каналы)
правит право `ops.manage`; проверка идёт раз в минуту на экземпляре с
планировщиком. Одно оповещение на инцидент, повтор не чаще заданного,
«відновлено» по окончании; история — 90 дней. Бэкап сервер не видит:
оповещение о нём — ненулевой код `scripts/verify-backup.sh` в системе
оповещений хоста (см. «Проверка восстановимости бэкапа»).

Там же — «Помилки клієнта» (падения экранов консоли и кабинета, сетевые
сбои, ошибки мобилки; без входа — не больше десяти за десять минут с
адреса) и «Швидкість екранів» (LCP, INP, CLS, TTFB и переход между
экранами у пятой части сессий консоли, p75 по маршруту и дню). Всё — без
ПДн: маршрут шаблоном, текст вычищен, браузер и ОС грубо.

## Смоук веб-консоли

Проверяет собранную консоль против живого API — то, чего юнит-тесты увидеть
не могут: что страница отрисовалась, кнопка дошла до сервера, сборка не
рассыпалась.

```
bun run e2e          # весь набор
bun run e2e:ui       # с браузером и пошаговым разбором
```

Стенд поднимается сам: API на 3199, консоль на 4199, база `quizzy_e2e`
пересоздаётся перед прогоном (`db:reset` + посев). Порты намеренно не
совпадают с dev — можно гонять, не гася рабочие серверы. Адрес базы берётся
из `apps/api/.env` с подменой имени БД; в CI задаётся `E2E_DATABASE_URL`.

**Смоук не запускать против клинической базы.** Первым делом он делает
`drop schema public cascade`; защита одна — отдельное имя БД в адресе.

При падении в CI отчёт лежит в артефакте `playwright-report`; локально —
`bunx playwright show-report`.

## Обновление

```bash
git pull && docker compose --env-file .env.docker up -d --build
```

Миграции применятся на старте API. Откат: `git checkout <sha>` + пересборка;
миграции назад не откатываются — восстанавливайтесь из бэкапа.
